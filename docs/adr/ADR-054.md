# ADR-054：任务层面下线归档，任务生命周期只剩 ACTIVE / INVALID

- 状态：Accepted
- 基线固化：2026-09-29
- 接受依据：用户 2026-09-29 明确要求「那就把这个功能去除掉」——承接其对任务编辑弹窗底部「归档」入口的追问「为什么编辑任务有个归档的功能，不是已经有完成任务和取消任务的功能了吗」与结论「我感觉这个任务的归档没有用处」。
- 替代：替代 [ADR-034](ADR-034.md) 中**任务归档与恢复**的全部决策（`archiveTask` / `restoreTask` / `archiveModuleTask` / `restoreModuleTask`、`TaskArchiveRequest`、审计动作 `task.archive` / `task.unarchive`、活动类型 `TASK_ARCHIVED` / `TASK_RESTORED`）。ADR-034 的项目归档申请—审核部分已由 [ADR-043](ADR-043.md) 替代、模块归档部分已由 [ADR-044](ADR-044.md) 替代、功能归档部分已由 [ADR-045](ADR-045.md) 替代，本 ADR 落地后 ADR-034 只剩历史价值。
- 修订：修订 [ADR-043](ADR-043.md)「维护中」门禁的实现口径（判定条件中的 `lifecycle_status = 'ACTIVE'` 不再是「排除已归档任务」，只表示「排除已标记无效的任务」，用户可见语义收敛为「存在未完成且未取消的任务则拒绝切换」）。

## 背景

1. 归档在任务层没有形成真实使用场景。任务已经有「完成」「取消」两条收尾路径，用户按它们收尾；`归档` 只是把任务从看板与看板统计里拿掉并让表单只读，既不收回任何权限，也不改变任何统计口径（完成数、未完成数、项目/模块/功能档位都不看 `lifecycle_status`）。
2. 归档的原始动机已经消失。ADR-034 引入它的关键理由是「模块归档与项目归档要求下级任务已收尾（当时口径为已归档）」；该前置校验先被 2026-09-16 的「已收尾 = DONE / CANCELED / ARCHIVED」放宽（归档不再是必要条件），随后 [ADR-043](ADR-043.md) 下线项目归档、[ADR-044](ADR-044.md) 下线模块归档、[ADR-045](ADR-045.md) 下线功能归档，归档彻底失去存在的理由。
3. 实测证据（2026-09-29，本地演示库 `app`，57 个任务）：`lifecycle_status = 'ARCHIVED'` 0 行；审计里仅有 1 条 `task.archive` 测试痕迹，`task.unarchive` 0 条。即完整演示数据中没有任何一次真实归档。
4. 保留它的成本是实打实的：4 条路由 + 1 个请求 Schema + 1 组前端入口与确认弹窗、任务服务里 3 个专用方法、仓储 `setLifecycle`、「父级已归档时仍允许归档任务」的特例授权分支，以及「任务已归档，表单只读；可用下方按钮恢复」这类与其它层级（项目/模块/功能都已无归档态）不一致的文案。

## 决策

### 1. 任务生命周期取值域收窄为 `ACTIVE | INVALID`

数据库 `tasks_lifecycle_status_check` 由 `IN ('ACTIVE', 'ARCHIVED', 'INVALID')` 收紧为 `IN ('ACTIVE', 'INVALID')`；`ACTIVE` 是唯一常规形态，`INVALID` 保留给「标记无效」这条独立语义（本次不动，见非目标第 1 条）。迁移 `0032_task_archive_removal.sql` 负责升级窗口：临时关闭 `tasks_row_version` 触发器把存量 `ARCHIVED` 行回填为 `ACTIVE`（不递增 `row_version`、不写审计），`SET CONSTRAINTS ALL IMMEDIATE` 结算延迟约束事件后立即恢复触发器，最后重建收紧的状态 CHECK。迁移不可逆，不做物理删列；历史迁移不改写。

### 2. 四条归档路由与原因 Schema 整体下线

- 路由：`archiveTask`、`restoreTask`、`archiveModuleTask`、`restoreModuleTask` 从 Schema Registry、Route Registry、权限矩阵、OpenAPI 与生成客户端移除（Route Registry 103 → 99 条）；删除后 `POST .../tasks/{taskId}/archive`、`/restore` 与模块级同形路径均返回 404（未匹配路由的固定文案 JSON 404）。
- Schema：`taskArchiveRequestSchema` / `TaskArchiveRequest` 整体删除，路由定义里 `**/tasks/{taskId}` 这一族不再有第二套请求体；`基本任务路由` 与 `模块任务路由` 的映射去掉 `lifecycle` 特例分支。
- DTO：`taskItemSchema`（含 `ModuleTaskItem`）的 `lifecycleStatus` 由 `["ACTIVE","ARCHIVED","INVALID"]` 收窄为 `["ACTIVE","INVALID"]`；聚合读 `MyTaskItem`（R-3）、`TaskGroupMembershipItem`（R-5）与记录草稿来源任务同一口径收窄。
- 幂等契约版本：`createTask` / `updateTask` / `createModuleTask` / `updateModuleTask` 由 `2.0.0` 升到 `3.0.0`，`transitionTask` / `transitionModuleTask` 由 `3.0.0` 升到 `4.0.0`（响应 Schema 收窄属破坏性变更，旧 Key 在新契约下 409）。

### 3. 后端归档机件整体删除

`TasksManagementService` 的 `TaskOperation` 收窄为 `createTask | updateTask | createModuleTask | updateModuleTask`，`isTaskLifecycleOperation`、`changeTaskLifecycle`、`requireArchiveRole` 与 `execute` 入参里的 `reason` 一并删除；`TaskManagementRepository.setLifecycle` 删除；`TasksHttpService` 不再传递 `reason`。任务的写前检查只剩「父级存在且归属正确」与「任务生命周期可写（`ACTIVE`，即排除 `INVALID`）」，`TASK_STATE_CONFLICT` 继续由「状态已变化」与「生命周期不可写」两条路径抛出。

### 4. 「维护中」门禁口径显式收敛

`ProjectsWritePort.countUnarchivedTasks`（ADR-043 的「维护中」前置校验）SQL 保持 `lifecycle_status = 'ACTIVE' AND work_status NOT IN ('DONE','CANCELED')` 不变，但语义收敛为：作用域内存在任何未完成且未取消（且未标记无效）的任务时拒绝切换，错误码仍为 409 `PROJECT_MAINTENANCE_TASKS_OPEN`。此前的「先把任务归档再切维护中」旁路随归档下线一并消失，这是本次唯一有用户可见影响的口径变化。

### 5. 读路径与统计口径不变

看板集合（`listForBoard`）与看板统计继续排除 `lifecycle_status <> 'ACTIVE'` 的任务，迁移后该条件只等价于「排除已标记无效的任务」；`effectiveOnly` 系列（任务中心、卡统计列）继续用 `lifecycle_status <> 'INVALID'`；搜索投影、活动、通知的既有逻辑不变（归档本来就不影响它们）。所有过滤条件本次不改写，避免无谓的行为漂移。

### 6. 前端只剩「编辑 / 完成 / 取消 / 重开 / 恢复」

- 任务编辑弹窗底部的 `task-modal-lifecycle` 按钮、归档/恢复确认弹窗（原因文本框与两条提示语）整体删除；「编辑任务」按钮恢复为仅由 `writable` 控制。
- 任务详情不再有「已归档」只读提示；只读只可能来自「调用方传入只读范围」或任务被标记无效，提示文案改为「任务已标记无效，表单只读。」（编辑重载冲突提示同理）。
- 聚合组详情的成员卡片删除「已归档」徽章分支；`my-tasks` 的类型与 mock 同步收窄。
- 任务相关的「归档 / 恢复」文案不再出现；`activity-labels.ts` 的 `TASK_ARCHIVED` / `TASK_RESTORED` / `PROJECT_ARCHIVED` 标签保留，仅用于历史动态行的只读展示（见非目标第 3 条）。

### 7. 非目标

1. 不动 `INVALID` 语义与它的读写路径：`lifecycleStatus !== "ACTIVE"` 的写入门禁、看板排除、任务中心排除、`TASK_MERGE_PARENT_ARCHIVED`（任务已归档或无效，不能合并）继续保留，错误码与消息文案本次按「已无效」表述调整措辞但不改码。
2. 不动完成 / 取消 / 重开 / 恢复四条状态迁移、状态历史、完成快照与统计口径。
3. 不清理历史审计、历史动态与历史通知中既有的 `task.archive` / `task.unarchive` 记录（含演示库里的 1 条），只保留只读展示；不删 `tasks.lifecycle_status` 列。
4. 不修改已合并的历史迁移（`0000`–`0031`），也不回改 ADR-034 的正文，只在其头部加修订说明与本 ADR 的引用。
