# ADR-078：更换机器人（botId 变化）时自动解除全部企业微信绑定

- 状态：Accepted（2026-10-15 接受，随本批落库）
- 日期：2026-10-15
- 决策人：项目负责人（用户指示）与开发代理共同确认
- 关联：修订 [ADR-070](ADR-070.md) 的保存语义（新增 botId 变化副作用），联动 [ADR-069](ADR-069.md) 个人绑定与 [ADR-077](ADR-077.md) 项目群绑定的生命周期；沿用 [ADR-013](ADR-013.md)（事务边界）、[ADR-023](ADR-023.md)（幂等模式）、[ADR-029](ADR-029.md)（统一错误体与响应校验）；新增迁移 `0045`；路由数不变（119 条）。

## 1. 背景

用户需求要点：

> 因为企业机器人需要对话一次才能激活，我现在需要你做更换了机器人就解绑

- 企业微信「智能机器人（API 模式 + 长连接）」的推送硬前提（官方文档 21663，2026-10-15 核实）：成员必须先与机器人有一次主动对话（群内先有人 @ 机器人），机器人才可向该会话推送。
- 管理员在「成员与设置 → 企业微信机器人」更换机器人（新的 botId / secret）后，旧的个人绑定与项目群绑定仍记录为 ACTIVE，但新机器人对这些会话一律推送失败：绑定变成「看似生效、实际不可投递」的脏状态，成员侧没有任何提示，也不会主动重新激活。
- 因此「更换机器人」必须伴随显式解绑：解除全部 ACTIVE 绑定后，成员重新生成绑定码并向新机器人发送（该动作即完成激活），项目群由组长 / 系统管理员重新绑定。

## 2. 决策

### 2.1 触发条件

- 仅当保存的 `botId` 与已存值不同（即「更换机器人」）时触发；仅轮换 Secret 或仅修改 `botProfileUrl` 不触发（同一机器人的激活关系不变）。
- 首次配置（不存在配置行）不触发：没有机器人可推送时不可能存在生效绑定。
- 判定在 `updateWecomRobotConfig` 同一事务内完成（此前已对单行配置 `SELECT ... FOR UPDATE`），不存在并发歧义。

### 2.2 数据库收口（迁移 0045）

- 新增 `app.revoke_wecom_bindings_on_robot_change()`：`SECURITY DEFINER`、`SET search_path = app, pg_catalog`；单事务内把 `app.user_wecom_bindings` 与 `app.project_wecom_groups` 的全部 ACTIVE 行置 `REVOKED`（`revoked_at = now()`、`updated_at = now()`、`row_version + 1`），返回两表解除计数。
- 状态流转保留历史，不物理删除任何行；不触碰两张绑定码表（未消费码由下次签发覆盖或自然过期）与 `app.wecom_group_deliveries`（未投递记录由桥接第二批按绑定状态处理）。
- `app_runtime` 只被授予 EXECUTE、PUBLIC 回收；迁移内 `DO $$` 部署断言校验函数定义者、显式 ACL 与最小授权（与 `app.purge_project` 同款窄口收口）。
- 不采用数据库触发器自动解绑：用户视角的「更换机器人」由应用判定，数据库只提供窄口函数，保持「应用服务判定业务语义、数据库兜底不变量」的分层。

### 2.3 API 与前端语义

- `updateWecomRobotConfig` 响应（`WecomRobotConfig`）新增两个可空字段：`revokedUserBindings`、`revokedProjectGroups`——未更换机器人为 `null`；更换时为本次解除的计数（可能为 `0`，与 `null` 语义区分）。GET 一律返回 `null`（计数只在保存响应出现）。
- 幂等契约版本 `1.1.0 → 1.2.0`：响应新增可安全重放字段，旧 Key 在新契约下 409；两个字段进入 `configReplayFields`（重放返回首次保存的计数，不重复解绑）。
- 审计 `admin.wecomRobot.update` payload 增加 `robotChanged` 与 `revokedUserBindings` / `revokedProjectGroups`（未更换为 `false` / `null`）。
- 管理页保存成功后，若发生更换则提示解绑计数与「相关成员与企业微信群需重新绑定（新机器人需要先对话激活）」；未更换时维持原提示。

### 2.4 与桥接的关系

- 桥接进程按 ACTIVE 绑定读取投递目标，绑定被解除后自动停止向旧会话推送——本批不需要桥接侧改动（未改 `deploy/test-vm/wecom-bridge/`）。
- 解绑只发生在本系统内：企业微信侧不存在「删除会话」操作，旧机器人仍可能被历史会话唤起，但不再收到 InPulse 的投递。

## 3. 安全与审计

- 解绑与配置保存同事务、同审计：任何异常都会整体回滚，不会出现「配置已换、绑定未解」或「绑定已解、配置未换」的中间状态。
- 响应只含计数，不泄露绑定对象身份（userid / chatid 不出现在管理响应与审计）。
- 权限矩阵不变：仍是完整管理员 Session + CSRF + 数据库级幂等；不新增路由、不新增角色。

## 4. 非目标

- 不做按机器人粒度的绑定迁移 / 恢复：解绑后一律重新走绑定码流程（激活是成员侧动作，系统无法代劳）。
- 不做群投递队列的级联清理（属 ADR-077 第二批桥接改造）。
- 不引入环境变量开关：更换机器人自动解绑是安全默认（fail closed），无配置项。
