# ADR-043：项目层面下线归档，生命周期收窄为未开始 / 进行中 / 维护中三态

- 状态：Accepted
- 基线固化：2026-09-23
- 接受依据：用户 2026-09-23 明确要求「在项目层面以后不存在归档这一说也不再需要申请，只有未开始，进行中和维护中。只有项目内所有的任务都呈现完成状态即可调整进入维护状态」。
- 替代：替代 [ADR-034](ADR-034.md) 中**项目归档申请—审核**的全部决策（F-06.2 项目归档申请、`requestProjectArchive` / `approveProjectArchive` / `rejectProjectArchive` / `getProjectArchivePreview` / `archiveProject` / `restoreProject`）。ADR-034 中「模块 / 功能 / 任务归档 + 父级归档前置校验」继续有效。
- 修订：修订 [ADR-035](ADR-035.md) 的项目状态口径，由四态收窄为三态；ADR-035 的粘性 `first_task_completed_at`、「未开始 ⇄ 维护中不可直接互改」与「已有完成任务不可回退未开始」三条不变量继续有效。

## 背景

1. 项目归档在落地后没有形成真实使用场景：项目需要长期承载模块、功能、任务与迭代记录，而「归档」只带来一个只读态和一整套申请—审批流程（发起、待审、批准、驳回、恢复）。实际协作里项目结束或转入低频维护时，团队需要的是「继续可用但不再排期」，不是「整块只读」。
2. 四态里的「维护中」正是这个语义，且它已经是唯一真相：主体已完成、只做小修小补。只要有「维护中」，「已归档」就只剩权限与流程成本：六条路由、一张申请表、两处待审提示与两次权限校验（申请与审核）。
3. 归档带来的只读态还有连带复杂度：项目写入口要先判断父级是否归档（`parent-not-active`），任务 / 记录 / 成员等 10 余处服务都要跟着分支；这些分支在「维护中仍可写」的口径下无法复用，只能各自维护。
4. 因此把「项目是否还可以写」的答案收敛为「不是三态的问题」：项目在三态下都可写，模块 / 功能 / 任务仍保留各自的归档（那是「从活跃视图移除但保留历史」的一级操作）。

## 决策

### 1. 项目状态只有三态，`ARCHIVED` 从项目域删除

```text
NOT_STARTED   未开始   项目下还没有任何已完成任务
ACTIVE        进行中   项目已开工
MAINTENANCE   维护中   主体已完成、只做小修小补；进入前要求项目下任务全部收尾
```

数据库 `projects_status_check` 收紧为三态；`app_runtime` 对 `app.project_archive_requests` 的 `INSERT` / `UPDATE` 权限收回。迁移 `0023_project_three_state.sql` 承接升级窗口，历史迁移不改写。

### 2. 存量 `ARCHIVED` 行的去向（与 0017 对称）

- `first_task_completed_at IS NOT NULL`（归档前确有产出）→ `MAINTENANCE`；
- `first_task_completed_at IS NULL`（归档前从未有任务完成）→ `NOT_STARTED`，与 0017 对 `ACTIVE` 行的回填口径一致，也天然满足 `projects_not_started_lock_check`。

`archived_at` 列保留（迁移不可逆，不做物理删除），但三态下必须恒为空：回填把非空值统一置 `NULL`，约束改写为 `projects_archived_at_null_check CHECK (archived_at IS NULL)` 作为兜底。

### 3. 六条归档路由与申请表整体下线

- 路由：`archiveProject`、`restoreProject`、`getProjectArchivePreview`、`requestProjectArchive`、`approveProjectArchive`、`rejectProjectArchive` 全部从 Schema Registry、Route Registry、权限矩阵、OpenAPI 与生成客户端移除。
- `projectListItemSchema` 去掉 `pendingArchiveRequest`；项目卡片不再有待审提示、批准、驳回或申请入口。
- `app.project_archive_requests` 表与历史行**原样保留**（业务历史不物理删除），只收回运行时的写权限；前端保留 `PROJECT_ARCHIVED` / `PROJECT_RESTORED` / `PROJECT_ARCHIVE_REQUESTED` / `PROJECT_ARCHIVE_REJECTED` 的展示文案，使历史动态与历史通知仍可读。

### 4. 「进入维护中」的前置门禁（本轮唯一的新增业务规则）

- 目标态为 `MAINTENANCE` 时，服务端统计项目下**未收尾**任务数：`lifecycle_status = 'ACTIVE'` 且 `work_status NOT IN ('DONE', 'CANCELED')`。
- 计数大于 0 时返回 409 `PROJECT_MAINTENANCE_TASKS_OPEN`，文案为「项目下仍有 N 个未完成、也未归档的任务，请先完成或归档全部任务再切换为维护中」。
- 口径与模块归档的「未收尾任务」完全一致（同一 SQL 只换错误码）；已归档或已取消的任务都不算未收尾。
- 门禁只作用于「进入维护中」。切到 `ACTIVE` 或回退到 `NOT_STARTED` 不受任务状态限制，仍只受既有两条不变量约束。

### 5. 保留的硬约束（不变）

- 未开始 ⇄ 维护中禁止直接互改 → 409 `PROJECT_STATUS_LEVEL_SKIP`；
- 出现过已完成任务（`first_task_completed_at` 非空）后不可回退未开始 → 409 `PROJECT_STATUS_NOT_STARTED_LOCKED`；
- 目标态等于当前态 → 409 `PROJECT_STATE_CONFLICT`；
- 项目生命周期操作仍要求 CSRF、`Idempotency-Key` 与 `If-Match`，并对全体活跃成员或系统管理员开放（ADR-039）。

### 6. 写权限口径随之统一

项目不再有只读态，因此所有「父级是项目」的写入口删除 `parent-not-active` 分支：`ProjectWriteCheckResult` 收窄为 `allowed | not-found`，未知生命周期值 fail closed 映射为 `not-found`（404）。模块 / 功能 / 任务自身的归档只读判定不变。

### 7. 非目标

1. 不删除模块、功能、任务的归档与恢复；模块归档仍要求该模块下全部任务都已归档。
2. 不新增项目状态、不做项目删除或物理清理。
3. 不改动 ADR-035 的粘性标记、自动升级（首次任务完成 → 进行中）与通知口径。
