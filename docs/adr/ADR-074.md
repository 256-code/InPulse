# ADR-074：api 容器增加仅出站 egress 网络（Casdoor SSO 与 AI 辅助外联）

- 状态：Accepted（2026-10-15 接受；2026-10-13 起已在测试环境实施，本批并入仓库基线）
- 日期：2026-10-15
- 决策人：项目负责人（用户指示）与开发代理共同确认
- 关联：补齐 [ADR-032](ADR-032.md)（Casdoor SSO）与 [ADR-067](ADR-067.md) / [ADR-068](ADR-068.md)（AI 辅助）在部署拓扑上的出网前提；沿用 [ADR-017](ADR-017.md)（固定版本与镜像 digest）的边界。**无新增路由、无数据库迁移、无新增依赖、无权限变化**；变更 `deploy/compose.yaml`（api 网络与 networks 段）、`技术设计v1.2.2.md` §11.2 内嵌 compose 片段、`deploy/test-vm/README.md` 与 `开发日志.md`。

## 1. 背景

`deploy/compose.yaml` 的 `backend` 是 `internal: true` 的静态子网（`172.30.0.0/24`），与 api 的 `TRUSTED_PROXY_CIDRS` 绑定：api 的唯一入站来源是 web(Nginx)，`req.ip`、审计 `ip_address` 与登录/SSO 的 IP 限流都依赖这条信任链。该网络没有外部网关，**api 因此没有外网出口**——只服务浏览器时没有影响，但两处既有能力需要 api 主动访问外部 HTTPS 端点：

- [ADR-032](ADR-032.md) 的 Casdoor SSO：OIDC discovery、token 交换与 JWKS 验签都在 api 进程内直连 issuer；
- [ADR-067](ADR-067.md) / [ADR-068](ADR-068.md) 的 AI 辅助：调用管理员在线配置的 AI 端点。

2026-10-13 测试 VM 开启 SSO 后，`GET /api/v1/auth/sso/start` 返回 `302 → /login?sso_error=internal`；排查结论是 api 容器拉取 `https://authtest.libiaorobot.com/.well-known/openid-configuration` 失败（容器无出网路由），而 VM 宿主机与默认网桥容器都可访问。为恢复 SSO，当时在测试 VM 的部署副本上实施了 `egress` 网络（VM 侧唯一的手工适配）。本 ADR 把该适配正式并入仓库基线，使仓库与测试环境拓扑一致。

## 2. 决策

### 2.1 新增仅 api 使用的出站网络 `egress`

`networks` 段在 `edge` 之后新增普通 bridge 网络（不设 `internal`、不约定静态子网）：

```yaml
  edge:
  # 仅 api 使用的出站网络（ADR-074）：SSO discovery/token/JWKS 与 AI 辅助外联
  # 需要访问外部 HTTPS 端点。不与 web/backup/audit-archive 共享，保证 web 解析
  # api 只得到 backend 地址，维持 TRUSTED_PROXY_CIDRS=172.30.0.0/24 的信任链语义。
  egress:
```

### 2.2 api 服务接入 `networks: [backend, egress]`

入站路径不变（web → backend 静态子网），出站走 `egress` 的默认网关。**web 不接入 `egress`**，因此 Nginx 解析 `api` 主机名只会得到 backend 地址，`TRUSTED_PROXY_CIDRS=172.30.0.0/24` 的语义、`apps/api/src/trusted-proxy.ts` 的 fail closed 校验与漂移风险说明完全不变。

### 2.3 备选方案与否决理由

- **把 api 加入既有 `edge` 网络**（web / backup / audit-archive 所在）：web 与 api 将共享两个网络，Nginx 启动时对 `api` 的解析会得到两个地址并轮询，一部分请求的源地址落在 `172.30.0.0/24` 之外，`req.ip`（审计与限流）失真；同时把 api 放进面向 80/443 映射的网络，扩大暴露面。
- **取消 `backend` 的 `internal` 标志**：db、migrate 等都在 `backend` 上，等于给整个栈开外网，并破坏「静态子网 + 唯一入站来源」的信任链设计。
- **引入 HTTP 转发代理或域名白名单网关**：属于 V1 非目标（不引入额外基础设施）。如未来需要更严格的出站策略，另行 ADR 评估。

### 2.4 安全边界

- 获得出站能力的只有 api；`db`、`migrate` 仍只在 `internal` 的 `backend` 上，`backup` / `audit-archive` 的网络维持既有 `[backend, edge]`（它们本就为异地推送出网）。
- api 的应用层只发起 SSO 与 AI 辅助两类外部请求；`egress` 不带静态子网、不映射端口，不改变任何入站行为。

## 3. 影响

- 仓库与测试环境的 `deploy/compose.yaml` 从此一致（此前 VM 侧存在唯一一处手工适配 `egress`，见 `deploy/test-vm/README.md`）。
- `scripts/check_deploy_refs.mjs`（`pnpm check:deploy:test`）的既有断言不变：它校验 `backend` 静态子网与镜像 ref 格式；`egress` 为普通网络，不需要新增断言。如未来给 `egress` 增加静态子网或网关限制，必须在预检中同步。
- 生产发布流程不变：镜像 tag/digest 绑定与签名仍按技术设计 §12 人工完成；本 ADR 只定义拓扑。

## 4. 验证

- 2026-10-13（测试 VM）：修复前 api 容器内 fetch Casdoor discovery 失败、`/api/v1/auth/sso/start` 返回 `sso_error=internal`；接入 `egress` 重建 api 后，容器内 fetch 返回 `200`，`/sso/start` 恢复 302 跳转 `https://authtest.libiaorobot.com/login/oauth/authorize`。
- 2026-10-15（本批并入仓库）：`pnpm check:deploy:test`、`pnpm check:docs`、`pnpm format:check`、`pnpm check:secrets` 与 VM 侧 `compose config --quiet` 的结果见开发日志第一百八十一条。

## 5. 本 ADR 未覆盖

- 生产环境的出站访问策略（转发代理、域名白名单、出站审计）未定义；生产发布时按技术设计 §12 与发布评审决定是否需要更严限制。
- 不改变 SSO 与 AI 辅助的功能行为；`sso_error=internal` 的其余成因（issuer 不一致、Secret 缺失或权限错误等）仍按技术设计 SSO 章节与部署手册排查。
