# ADR-036：任务列表排序口径统一（紧急度优先 + 状态分组）与多列 keyset 游标

- 状态：Proposed（待人工批准）
- 提出：2026-09-18
- 替代 / 收紧：[聚合读契约提案](../c-aggregate-read-contract-proposal.md) Q-10「固定 `ORDER BY t.id DESC`，不提供 `sort`」与 [A 裁决 Q-10](../a-contract-review-f25-f29-f32.md) 的同一结论；C-006 游标在 `MY_TASKS` 命名空间下的载荷由单列 `afterId` 扩展为多列 keyset。排序值本身、游标签名绑定 actor 与筛选条件、TTL 15 分钟、`limit` 默认 20 上限 100 均不变。

## 背景

1. Q-10 定案时只解决「稳定 + 命中现有索引」：`tasks_project_status_idx` 与 `tasks_assignee_status_idx` 的末列是 `id`（`database/migrations/0000_initial.sql:727-728`），`ORDER BY t.id DESC` 无需新增迁移。当时没有排序业务需求，因此用「不提供 `sort`」把问题冻结。
2. 2026-09-18 人工确认要按业务紧急度排序。最终口径（同一日人工确认）：已逾期 → 遗留问题来源 → 标记紧急 → 今/明日截止 → 其余；整体按 未完成 → 已完成 → 已取消 分组。
3. 任务面板（功能页 / 模块任务页）此前已按「状态分组 + 优先级」排序，任务中心仍是 `id DESC`：同一批任务在两处顺序不同，「紧急 / 逾期 / 遗留问题」在任务中心完全不可见。本 ADR 用同一排序键取代两处各自的定义。
4. 任务中心是分页 + 签名游标：排序键从单列 `id` 变成多列元组后，`t.id < afterTaskId` 不再等价于「取下一页」，游标载荷必须同步升级，否则翻页会漏项或重项。

## 决策

### 1. 统一排序键（任务中心与任务面板完全一致）

```text
状态分组   未完成(0) → 已完成(1) → 已取消(2)
紧急桶     仅未完成参与，命中第一个：已逾期(0) → 遗留问题来源(1) → 标记紧急(2) → 今/明日截止(3) → 其余(4)
优先级     紧急(0) → 高(1) → 普通(2) → 低(3)
截止时间   due_at ASC NULLS LAST
任务 ID    id ASC（唯一兜底，保证刷新前后稳定）
```

- 「今天 / 明天 / 已逾期」按 `Asia/Shanghai` 的日历日由服务端计算，与任务中心 `dueToday` 统计、任务看板 `dueState` 同一时区口径；前端不得按客户端时钟重算（技术设计 §R-3 既有约定）。
- 已逾期 = `due_at` 早于今天 00:00；今 / 明日截止 = `due_at` 落在 [今天 00:00, 后天 00:00)。
- 遗留问题来源 = `app.leftover_task_links` 存在指向该任务的链接，判定与前端 `hasLeftoverSource` 同源；V1 不区分遗留项当前状态，也不要求必须来自 CONVERTED 遗留项。
- 已完成、已取消不参与紧急桶：逾期或今日截止不会把已完成的任务拉到最前；它们在各自分组内仍按 优先级 → 截止时间 → id。
- 紧急桶按「命中第一个」判定，一条任务只占一个桶，避免同一任务被重复计入相邻桶导致顺序抖动。
- 单一实现：排序键、`ORDER BY`、keyset 断页与游标载荷编码集中在 `app/api/src/modules/tasks/task-list-order.ts`，任务中心、任务面板与 `TaskQueryPort` 共用；禁止各端口再定义自己的 `ORDER BY`（`TaskManagementRepository` 原有的 `panelOrderBy` 已删除）。
- 排序固定，仍不提供 `sort` 参数：Q-10 的「客户端不得指定排序」结论保留，只改固定口径。

### 2. 游标升级（C-006 载荷扩展）

- `MY_TASKS` 命名空间的游标载荷新增 `k`：规范化的排序键元组 `状态分组|紧急桶|优先级|截止时间(ISO 或空)|任务ID`，JSON 规范化后一并进入 HMAC 签名，与 actor、namespace、filterKey、TTL 15 分钟同时校验。
- `MY_TASKS` 下缺少 `k` 的旧载荷一律按无效游标 422 拒绝（`AGGREGATE_READ_INVALID_CURSOR`），不得静默按新排序断页——静默会直接产生翻页漏项 / 重项。
- 其它命名空间（`TASK_GROUP_RECORDS` / `LEFTOVER_ITEMS` / `TASK_GROUPS`）不变，继续只用单列 `afterId`。
- 端口契约：`MyTaskQueryPort.list` 的入参 `afterTaskId` 与返回 `nextTaskId` 由单列改为排序键元组（`after` / `next`）；端口仍只接受已解码的位置、不负责签名（与 `ActivityProjectionReader` + `TimeCursorService` 同一分工）。
- SQL 断页条件改为与 ORDER BY 同构的多列 keyset 比较，并用 `COALESCE(due_at, `````` + INF + ``````)` 归一 `NULL`，避免 NULL 行既排最后又能被逐列比较重复命中。
- 不变：先过滤后分页、统计卡片与筛选无关、`limit` 默认 20 上限 100、游标绑定 actor 与全部筛选条件。

### 3. 作用范围

- 变更：`MyTaskQueryPort.list`（`GET /api/v1/tasks` 与 `GET /api/v1/me/tasks` 共用同一服务）、`TaskQueryPort.list`（保留同口径；该方法当前未被生产代码调用，仅测试引用）、`TaskManagementRepository.list`（改为复用同一排序键表达式）。
- 不变：任务看板 `listForBoard` 的「逾期 → 截止 → 已完成 → 已取消」口径、项目 / 模块 / 功能列表的生命周期排序、遗留问题列表排序。

### 4. 索引与性能

- 新排序键无法直接命中现有两个索引的排序尾（两者都以 `id` 收尾），任务中心是在「授权项目集合 + 筛选」之后做 top-N 排序。
- 阶段 0 的数据量与 `limit ≤ 100` 下先不新增索引；若 `EXPLAIN (ANALYZE, BUFFERS)` 证明排序成为瓶颈，再以「只补索引、不动排序」的独立变更处理，并附执行计划证据。
- 不得为排序引入 Redis、物化视图或通用缓存（系统设计非目标）。

### 5. 与「逾期」筛选口径的差异（未决，先记录）

- 现有 `overdue=true` 筛选用 `t.due_at < now()`（今天已过时刻即算逾期），本决策的「已逾期」桶按日历日；对「今天但时刻已过」的任务两者结论不同。
- 本 ADR 提议：排序按日历日（与卡片徽章 `dueInfo` 一致），筛选口径保持现状，差异先记录在案；若要统一，需另行变更筛选语义并同步前端徽章与统计卡片。

### 6. 测试要求

- 真实 PostgreSQL：覆盖 5 个紧急桶与 3 个状态分组的组合，断言返回顺序；反事实验证把排序退回 `id DESC` 时用例失败。
- 游标：跨页翻页不漏不重（含 `due_at IS NULL` 与完全并列的行）；旧载荷 422；篡改 / 跨 actor / 筛选变化 422。
- Web：任务中心首屏顺序与卡片上的状态、优先级、截止徽章一致。

### 7. 前置缺陷修复：原生 `sql` 的 `Date` 参数编码

- 现象：把 JS `Date` 作为参数传给 postgres.js 原生 `sql` 标签模板时，Bind 阶段抛 `The "string" argument must be of type string or an instance of Buffer or ArrayBuffer. Received an instance of Date`。本 ADR 的 keyset 是本仓库第一次在原生 SQL 里绑定 `Date`，因此由它暴露。
- 根因：drizzle-orm 的 postgres-js 驱动在 `construct()` 中把 `client.options.serializers` 的日期类型（1184/1082/1114 等）改写为恒等函数（日期编码交给它自己的列映射），而 postgres.js 的连接、原生 `sql` 与 Drizzle 共用同一个 options 对象；被改写后原生 `sql` 不再有 timestamptz 编码器。`apps/api/src/database/unit-of-work.ts` 为让 Drizzle 拿到 `options` 而复用父连接 options，使该改写同样作用于事务内的原生 `sql`。
- 修复：新增 `createDrizzleDb(sql)`（`database/src/client.ts`），在 Drizzle 构造后只还原 `timestamptz`（1184）一个编码器——postgres.js 只会把 JS `Date` 推断成 1184，而 Drizzle 的日期列在映射阶段已先行把值转成 ISO 字符串（字符串经过两种编码器结果一致）；JSON（114/3802）保持 Drizzle 的恒等函数，避免与 Drizzle 自身的 `JSON.stringify` 叠加成二次编码。
- 影响面：仅「原生 `sql` 绑定 JS `Date`」从崩溃变为可用；Drizzle 的读写路径与日期列解析（parsers 仍为恒等）不变。
