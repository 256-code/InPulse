# ADR-069：企业微信机器人绑定（一次性绑定码，阶段一）

- 状态：Accepted（2026-10-13 接受，实现随本批落库）
- 日期：2026-10-13
- 决策人：项目负责人（用户指示）与开发代理共同确认
- 关联：扩展 [ADR-023](ADR-023.md) allowlist（新增签发一次性安全材料的 `createWecomBindingCode`）；沿用 [ADR-004](ADR-004.md)（契约生成）、[ADR-013](ADR-013.md)（事务边界）、[ADR-029](ADR-029.md)（统一错误体与响应校验）；新增迁移 `0041`；新增 3 条路由（110 → 113）。阶段二的投递服务另立 ADR，不在本批。

## 1. 背景

用户需求要点：

> 我想通过企业微信的智能机器人和这个项目的通知接上……我想要的是当任务被指派到某个人，那个人会收到消息
> 现在在这里做个绑定企微机器人的功能

- 站内通知（F-28）已落库；企业微信「智能机器人（API 模式 + 长连接）」已在用户企业微信侧建立，桥接 PoC 证实：长连接可收用户消息、可主动推送（`aibot_send_msg`），但主动推送要求用户先打开过机器人，且企微侧只认 `userid`。
- 因此系统必须先把「InPulse 账号 ↔ 企微 userid」可靠绑定，才可能投递任务指派等通知；绑定不能靠管理员手工登记 userid（不可获取、易漂移）。
- 本期拆分：阶段一（本 ADR，本批实现）自助绑定；阶段二（未实现）投递——长连接桥接侧订阅通知事件并调用 `aibot_send_msg` 推送。

## 2. 决策

### 2.1 三条自助路由（`/api/v1/me/wecom-binding`）

- `GET /me/wecom-binding`（`getWecomBinding`）：返回三态 `UNBOUND` / `PENDING` / `BOUND` 与 `boundAt` / `codeExpiresAt`；身份只从 Session Cookie 解析；响应 `no-store`；`csrfPolicy: none`、`idempotencyPolicy: none`。
- `POST /me/wecom-binding/codes`（`createWecomBindingCode`）：签发 16 位 Crockford Base32（去 I / L / O / U）一次性绑定码——10 字节随机 = 80 bit 熵、`XXXX-XXXX-XXXX-XXXX` 格式、10 分钟有效；重新签发覆盖旧行、旧码立即失效；明文只在 201 响应返回一次，服务端只存 SHA-256（32 字节）；CSRF 必填；不进入通用幂等记录，加入 [ADR-023](ADR-023.md) allowlist（签发一次性安全材料，`securityFlow`），契约保证「重复请求即重新签发、无重放歧义」。
- `DELETE /me/wecom-binding`（`deleteWecomBinding`）：同一事务内作废待用码 + 把 ACTIVE 绑定置 `REVOKED`（状态流转，不物理删除）；CSRF + `Idempotency-Key` 必填，数据库级幂等、`replayAuthorizationPolicy: actorOnly`、204 无 body。
- 三条路由都只读写当前登录用户自己的绑定数据，不接受客户端指定用户，无管理员代绑面；路由总数 110 → 113。

### 2.2 数据模型（迁移 0041）

- `app.wecom_binding_codes`：`user_id` 主键（每用户至多一行当前待用码）；`code_hash BYTEA` 唯一且固定 32 字节；`expires_at > created_at`；`consumed_at` / `consumed_by_wecom_userid`（被重新签发或解绑作废时 `consumed_by` 为空）。
- `app.user_wecom_bindings`：`status ∈ {ACTIVE, REVOKED}` 且与 `revoked_at` 一致（CHECK）；部分唯一索引保证「同一用户至多一条 ACTIVE」「同一企微 userid 至多一条 ACTIVE」；行含 `row_version`（更新触发器要求恰好 +1）；解绑只改状态，重绑更新原行。
- `app.redeem_wecom_binding_code(p_code_hash BYTEA, p_wecom_userid TEXT)`：`SECURITY DEFINER`、`SET search_path = app, pg_catalog`；单事务内按 `code_hash` 取行 `FOR UPDATE` → 校验 → 用户 ACTIVE → 冲突检查 → 更新或插入绑定 → 条件消费绑定码；错误码固定：`WBC01` 无效码 / `WBC02` 已使用 / `WBC03` 参数非法 / `WBC04` 用户已停用 / `WBC05` 已过期 / `WBC06` 企微账号已绑定其它账号；唯一索引兜底并统一映射 `WBC06`。函数不做任何网络调用。
- 授权：`REVOKE ALL ... FROM PUBLIC`、只 `GRANT EXECUTE ... TO app_runtime`；两张表 `app_runtime` 只有 SELECT / INSERT / UPDATE（无 DELETE）、`app_backup` 只读；迁移内 `DO $$` 部署断言兜底。

### 2.3 前端交互

- 账户菜单（左下头像弹层）新增「绑定企业微信」，弹窗三态：
  - `UNBOUND`：步骤引导 + 「生成绑定码」；
  - 生成后：等宽大字显示一次性码 + 剩余有效期倒计时 + 「复制绑定码」，固定提示「把绑定码发送给企业微信里的 InPulse 机器人」；待用码存在期间每 5 秒轮询状态，用户发送后弹窗自动切到「已绑定」；
  - 若客户端没有明文（重开弹窗且服务端仍有待用码）：显示有效期并提示「重新生成」；
  - `BOUND`：显示绑定时间 + 「解除绑定」（Popconfirm 二次确认）。
- 所有请求经生成客户端；写操作先签发 CSRF，解绑携带一次性 `Idempotency-Key`；组件不裸写 fetch。

### 2.4 安全边界

- 绑定码 80 bit 随机、只存 Hash、10 分钟一次性；不进入日志 / 审计 / 幂等物化；响应 `no-store`。
- 解绑与重新签发的锁序固定为「先码行、后绑定行」，与兑换函数一致，避免与并发兑换互相持锁。
- 无跨用户枚举面：`WBC06` 只说明冲突，不暴露对方身份。
- 桥接进程以 `app_runtime` 身份调用兑换函数；投递凭证（botId / secret）由桥接侧持有，不进入 InPulse 数据库。

## 3. 非目标

- 阶段二投递（长连接桥接、按绑定关系推送站内通知、失败重试与可观测性）不在本批；本批不建投递队列表、不引入 Worker / Outbox、不加定时任务（保持既有非目标）。
- 不做管理员代绑 / 代解绑、绑定看板、企微通讯录同步、部门与角色映射。
- 不做绑定码的手工作废接口（重新生成与解绑已覆盖）；不做邮件 / 短信等其它通道。

## 5. 影响

- 路由 110 → 113；迁移新增 `0041`；权限矩阵新增 3 行与 1 条 security flow 记录。
- 用户从此可自助绑定 / 解绑企业微信；阶段二投递落地后，任务指派等站内通知可按绑定关系推送到企微。
