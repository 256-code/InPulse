# ADR-028：apps/api 迁移至 ESM/NodeNext 以消费共享 ESM 包

- 状态：Proposed
- 提出日期：2026-09-07
- 关联：[ADR-005](ADR-005.md)、[ADR-013](ADR-013.md)、[ADR-026](ADR-026.md)、[ADR-027](ADR-027.md)
- 性质：本记录是「API 应用如何消费共享 ESM 包」的定案材料。转为 `Accepted` 前须通过第 7 节评审清单，并由非作者人工确认（作者不得自批）。

## 背景

`apps/api` 当前编译配置为 `module: CommonJS` + `moduleResolution: Node10`（见 `apps/api/tsconfig.json`，覆盖了基线的 `module: NodeNext`）。而 `@inpulse/database` 与 `@inpulse/api-contract` 均为 ESM（`"type": "module"`）且只通过 `exports` 指向 `.ts` 源文件，没有 `main`/`types`。

Node10 解析不识别 `exports` 字段，因此 `apps/api` 无法 `import ... from "@inpulse/database/client"`（源在 `src/client.ts`，npm 子路径解析不到），实测会报 TS2307；即便绕过类型检查，生产构建 `tsc` 产出的 CommonJS `require("@inpulse/database/client")` 也会指向一个 `.ts` 文件，`node dist/main.js` 无法执行。

[ADR-026](ADR-026.md) 已明确记录这一矛盾：“ESM-only 第三方包与 `apps/api` 现有 `moduleResolution: Node10` 的矛盾独立于本决策……引入此类依赖前必须先决定 moduleResolution 或选用 CJS 版本，不得假设它随 NestJS 版本变化而消失。”

阶段 1 的 F-11 需要 `apps/api` 接入 `@inpulse/database`（schema + client）以构建 `DatabaseModule` 与 `UnitOfWork/TransactionContext`，因此必须先定案 API 应用的模块化/解析策略，而不能由实现默认成为既成事实。

## 决策

1. **模块与解析**：`apps/api` 采用 ESM。`apps/api/tsconfig.json` 设为 `module: NodeNext`、`moduleResolution: NodeNext`（继承 `tsconfig.base.json` 的 `target: ES2024`、`strict` 与 `verbatimModuleSyntax`），并在 `apps/api/package.json` 增加 `"type": "module"`。
2. **相对导入**：所有 `apps/api/src` 内的相对导入使用 `.js` 扩展名（NodeNext/ESM 要求），例如 `./health/health.controller.js`、`./app.module.js`。
3. **运行与测试**：开发与测试仍经 `tsx`/`vitest` 解析 TS 源；生产构建 `pnpm --filter @inpulse/api build` 产出 ESM 到 `dist`，运行入口 `node dist/main.js`。NestJS 11.2.3 的 ESM 运行时路径已由 [ADR-026](ADR-026.md) Pod 验证可用。
4. **共享包消费**：`apps/api` 通过 `@inpulse/database`（`./client` 导出 `createDatabaseClient`）与后续的 `./config` 读取连接串，不再以字符重写一份 schema。
5. **CI 顺序**：依赖 `@inpulse/database` 编译或源码解析的前提随本决策确定；若共享包仍需编译产物，则相应调整 CI 构建顺序（database 先于 api），具体见第 7 节。

## 替代方案与权衡

| 维度 | 已选 | 主要替代方案 | 取舍 |
| --- | --- | --- | --- |
| API 模块制式 | ESM / NodeNext | 保持 CommonJS + Node10，另把 `@inpulse/database` 编译为 CJS 产物 | 保持 App CJS 则治理成本更低，但要给共享包加独立构建、改导出面并重排 CI；ESM 是 Node 与共享包自然形态，且 ADR-026 已验证 NestJS 11.2.3 ESM 路径可用，长期更省心。 |
| Schema 共享 | 直接消费 `@inpulse/database` schema | 在 `apps/api` 内用 `postgres + drizzle` 重写 schema | 重写会破坏 schema 单一真相、与迁移漂移，属于重复维护；不推荐。 |
| 运行时 | 生产 `node dist/main.js`（ESM） | 打包器（esbuild/tsup/esbuild）产单一产物 | 引入打包器与 tree-shaking 收益有限，且与 Nest 标准运行路径不一致；本期不引入。 |

## 后果

**正面：**
- `apps/api` 能直接消费 `@inpulse/database`、`@inpulse/api-contract` 等 ESM 共享包，为 `DatabaseModule/UnitOfWork` 与后续契约绑定扫清障碍。
- 与共享包、前端（Vite/ESM）一致，避免 Node10 解析与 `exports` 的长期摩擦。
- NestJS 11.2.3 的 ESM 路径已过 ADR-026 Pod 验证，风险有据可依。

**代价与风险：**
- 所有 `apps/api/src` 相对导入需补 `.js` 后缀，改动面集中在少量文件，但需全量重跑 typecheck/build/单测。
- 生产从 `node dist/main.js` 启动，需确认 `reflect-metadata`、`@nestjs/*`、`rxjs` 等 CJS 包在 ESM 下正确加载（ADR-026 已覆盖）。
- 若引入需要 `exports` 才能解析的纯 ESM 依赖，需在测试壳与运行参数中统一口径。
- `network` / healthcheck / 部署相关脚本可能假设 CommonJS 入口，需同步核对（阶段 0 尚无生产 Dockerfile）。

## 本 ADR 未决范围

- **契约运行期参数**：Nest Zod Pipe/Serializer 组合与运行参数、运行期 operationId → Nest 端点绑定仍属 `AGENTS.md` 第 4 节未定案项，本 ADR 只决定模块制式，不决定 Pipe/Serializer 细节。
- **`DatabaseModule` 与 `UnitOfWork` 的接口与实现**：属 F-11 实现，在本 ADR 转 `Accepted` 后单独立项。

## 影响与验证

- 本 ADR 为 `Proposed`：迁移尚未实施。正文决策是评审依据，不代表已完成 `apps/api` 的 ESM 化。
- 实际执行与验证将在本 ADR 转 `Accepted` 后的独立实现 PR 中完成，并如实记录 `pnpm typecheck`、`pnpm --filter @inpulse/api build`、`pnpm test:unit`、`node dist/main.js` 与 `apps/api` 成功 `import "@inpulse/database"` 的结果。

## 转为 Accepted 前的评审清单

评审人在把状态改为 `Accepted` 前，须逐项确认：

1. 在具备联网环境执行 `pnpm install --frozen-lockfile` 后，按技术设计 §12.4 顺序运行 `pnpm typecheck`、`pnpm --filter @inpulse/api build`、`pnpm test:unit`、`pnpm test:web`、`pnpm contract:drift`、`pnpm contract:validate`、`pnpm permissions:check`，全部通过；对应 PR 的 `CI / workspace` 通过。
2. 确认 `apps/api` 已为 `"type": "module"`、tsconfig 为 `module: NodeNext`/`moduleResolution: NodeNext`，所有相对导入带 `.js` 后缀。
3. 确认 `node dist/main.js` 能正常启动并响应 `/api/v1/health`；`@nestjs/*`、`reflect-metadata`、`rxjs` 在 ESM 下加载正常。
4. 确认 `apps/api` 能 `import { createDatabaseClient } from "@inpulse/database/client"`（或等价公开出口），且未重复维护 schema。
5. 确认未引入第三方面向打包器（esbuild/tsup 等）作为必然运行时依赖，也未把共享包编译产物手工写进 `apps/api`。
6. 确认 CI 构建顺序与依赖关系一致（涉及共享包编译时 database 先于 api），`pnpm-lock.yaml` 随依赖变更提交。
7. 非作者人工评审并批准（共享契约与数据库基建可由 B 或 C 评审），再将状态改为 `Accepted`，并同步把 `AGENTS.md`、`CONTRIBUTING.md`、`README.md` 中仍称 `Proposed` 的表述更新。
