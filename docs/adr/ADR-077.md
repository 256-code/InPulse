# ADR-077：企业微信项目群绑定（项目 ↔ 群，第一批）

- 状态：Accepted（2026-10-15 接受，首批实现随本批落库）
- 日期：2026-10-15
- 决策人：项目负责人（用户指示）与开发代理共同确认
- 关联：扩展 [ADR-023](ADR-023.md) allowlist（新增签发一次性安全材料的 `createProjectWecomGroupCode`）；扩展 [ADR-039](ADR-039.md) 的项目内管理例外清单（组长 + 系统管理员专属的 `wecomGroupBinderRole`）；复用 [ADR-069](ADR-069.md) 的绑定码编码 / 哈希 / TTL 规则与 [ADR-070](ADR-070.md) 的 `bot_profile_url`；沿用 [ADR-013](ADR-013.md)（事务边界）、[ADR-029](ADR-029.md)（统一错误体与响应校验）；新增迁移 `0044`；新增 3 条路由（116 → 119）。长连接桥接侧的群消息回调与 `chat_type:2` 投递改造为第二批，不在本批。

## 1. 背景

用户需求要点：

> 机器人能做到项目和群聊绑定吗，就是项目里面有变动或者任务派发就发送到对应项目群聊里
> 项目组长 + 系统管理员生成绑定码/解绑，先默认发「任务派发 + 全部 MEMBER 可见动态」，群推送与现有个人单聊并存，一个项目一个群、一个群一个项目

- 阶段一 / 阶段二（ADR-069 / ADR-070）已实现「InPulse 账号 ↔ 企微 userid」个人绑定、个人通知投递（桥接推送）与机器人凭据的管理员在线配置。
- 企业微信「智能机器人（API 模式 + 长连接）」的群推送事实（官方文档 21663，2026-10-15 核实）：机器人可被拉入内部群；群消息回调携带不可自行构造的 `chatid`；主动推送群消息使用 `aibot_send_msg` 且 `chat_type:2` 时以 `chatid` 为目标；**硬前提是群内先有人 @机器人 发过消息**，机器人才能获得该群的 `chatid` 并发消息；限速 30 条/分钟、1000 条/小时；单个机器人只能保持一条长连接。
- 因此「项目 ↔ 群」不能靠管理员手工登记群 id（不可获取、易漂移），必须与个人绑定同构：项目侧签发一次性绑定码，在目标群里 @机器人 发送该码完成绑定；兑换发生在长连接桥接侧，由数据库函数在单事务内完成。

## 2. 决策

### 2.1 三条项目级路由（`/api/v1/projects/{projectId}/wecom-group`）

- `GET /projects/{projectId}/wecom-group`（`getProjectWecomGroup`）：读取绑定三态（`UNBOUND` / `PENDING` / `BOUND`）、待用码过期时间、绑定时间与绑定人、桥接侧最近投递错误（`lastDeliveryError`）与机器人资料链接（`botProfileUrl`，来自 `app.wecom_robot_config`）；本项目活跃成员或系统管理员可读，非成员 / 已移除一律 404（与「资源不存在」不可区分）；响应 `no-store`；`csrfPolicy: none`、`idempotencyPolicy: none`。
- `POST /projects/{projectId}/wecom-group/codes`（`createProjectWecomGroupCode`）：签发 16 位 Crockford Base32（去 I / L / O / U，80 bit 熵）一次性绑定码，`XXXX-XXXX-XXXX-XXXX` 格式、10 分钟有效；重新签发覆盖旧码并立即作废旧码；明文只在 201 响应返回一次，服务端只存 SHA-256（32 字节）；CSRF 与同源必填；加入 [ADR-023](ADR-023.md) allowlist（`securityFlow` 第七条），不进入通用幂等记录；**仅系统管理员或本项目组长**（普通成员 403 `PROJECT_WECOM_GROUP_FORBIDDEN`，非成员 404）。
- `DELETE /projects/{projectId}/wecom-group`（`deleteProjectWecomGroup`）：同一事务内作废待用码并把 ACTIVE 绑定置 `REVOKED`（状态流转，不物理删除；重新绑定生成新绑定行、旧行保留投递历史）；CSRF + `Idempotency-Key` 必填，数据库级幂等（契约 1.0.0）、重放授权按「原始组长 / 管理员 + 目标项目」复核当前成员关系；204 无 body；写审计 `project.wecomGroup.unbind`（含是否确有绑定、群绑定行 id、待用码是否作废，不含任何密钥材料）。**仅系统管理员或本项目组长**（同签发门禁）。
- 门禁实现：`ProjectRoleGateService.wecomGroupBinderRole`（ADR-039 例外清单新增一处，与 `roleSetterRole` / `projectDeleterRole` / `scopeDeleterRole` 同源但单独成方法）；读路径走 `checkProjectForWrite` 的成员 / 管理员判定，写路径再叠加组长 / 管理员角色门禁。
- 路由总数 116 → 119；本批只落数据面与交互面，**不产生任何群投递**。

### 2.2 数据模型（迁移 0044）

- `app.project_wecom_binding_codes`：`project_id` 主键（每个项目至多一行当前待用码）；`code_hash BYTEA` 唯一且固定 32 字节；`expires_at > created_at`；`consumed_at` / `consumed_by_wecom_userid` / `consumed_by_user_id`（被重新签发、被解绑作废或已兑换时非空）。
- `app.project_wecom_groups`：`project_id` + `wecom_chat_id` + `bound_by_user_id` + `status ∈ {ACTIVE, REVOKED}` + `bound_at` / `revoked_at`（CHECK 与状态一致）+ `last_delivery_error`（≤500，桥接侧回写）+ `row_version`；部分唯一索引保证「同一项目至多一条 ACTIVE」「同一个群至多一条 ACTIVE」；解绑只改状态，换绑 = 旧行 REVOKED + 新行 ACTIVE。
- `app.wecom_group_deliveries`：投递状态表，按（绑定行，来源类型 `ACTIVITY` / `NOTIFICATION`，来源 id）唯一去重，`PENDING / SENT / FAILED` + `attempts` + `last_error` + 部分索引；桥接重启后可从 PENDING 断点续传。本迁移只落表与授权，写入方为下一批桥接改造。
- `app.redeem_project_wecom_binding_code(p_code_hash, p_wecom_chat_id, p_wecom_userid)`：`SECURITY DEFINER`、`SET search_path = app, pg_catalog`；单事务内锁序固定为「码行 → 发送者个人绑定行 → 群绑定行（先 chat 后 project）」；校验发送者个人绑定 ACTIVE 且用户未停用（PWG03）、项目成员身份（系统管理员豁免，PWG04）、群冲突（PWG05）与换绑语义；同群重复兑换同一项目幂等（只消费码）；错误码固定 PWG01 无效码 / PWG02 已使用 / PWG03 无可用个人绑定 / PWG04 非成员 / PWG05 群已绑其他项目 / PWG06 已过期 / PWG07 参数非法 / PWG08 并发冲突；函数不做任何网络调用。
- 项目物理删除（`app.purge_project`）同步清理三张表，迁移内重定义函数体并在 `DO $$` 部署断言中校验删除清单与索引、授权（`app_runtime` 无 DELETE、`app_backup` 只读）齐备。

### 2.3 投递范围（第二批桥接改造的目标口径）

- 默认投递两类来源：① 任务派发（`app.notifications` 的 `task.assigned`）；② 全部 MEMBER 可见的项目动态（`app.activity_projection` 中 `visibility_scope = 'MEMBER'`）。ADMIN_ONLY 动态不进入群推送。
- 群推送与现有个人单聊**并存**：个人绑定继续走单聊 `chat_type:1`，项目群绑定额外走 `chat_type:2`；同一事件可以两条通道各发一次，互不替代。
- 一个项目至多绑一个群、一个群至多绑一个项目（数据库部分唯一索引兜底）。
- 未做真 @（正文写姓名；真 @ 需要成员 userid 与企微 @ 语法支持，属后续增强）。
- 限速口径：机器人 30 条/分钟、1000 条/小时；桥接侧按 `app.wecom_group_deliveries` 的 PENDING 队列顺序投递并在超限时退避，失败原因写回 `last_error` 与绑定行 `last_delivery_error`（截断到 500 字符）。

### 2.4 前端交互（本批）

- 项目成员页新增「企业微信项目群」卡片：UNBOUND / PENDING / BOUND 三态；组长与系统管理员可见「生成绑定码」「解绑」操作，普通成员只读；展示待用码明文（一次性，含倒计时与复制）、绑定时间与绑定人、桥接侧最近投递错误、机器人资料链接与「先在企业微信群里 @机器人 发一条消息（机器人入群后首次获得该群）再发送绑定码」的固定引导；解绑用 Popconfirm 二次确认。
- 所有调用走生成客户端；写操作先签发 CSRF，解绑携带一次性 `Idempotency-Key`。

## 3. 安全与审计

- 绑定码只存 Hash；明文只返回一次且 `Cache-Control: no-store`；码为 80 bit 随机值、10 分钟有效、一次性消费。
- 门禁与读路径都不信任客户端提交的项目归属：成员关系与组长身份每请求在服务端实时读取（不缓存进 Session）；非成员统一 404。
- 解绑写审计 `project.wecomGroup.unbind`；签发绑定码按 ADR-069 先例不写审计（不改变持久化绑定状态）。
- 兑换函数 PUBLIC 执行权回收，仅 `app_runtime` 可执行；桥接进程只持有运行时凭据，不需要 DDL 权限。

## 4. 非目标与后续批次

- 本批不改造桥接进程（`chat_type:2` 发送、群消息回调中的绑定码兑换、投递队列消费均为第二批，且不要求本仓库改动即可先行落地数据面）。
- 不做真 @、不做群内反向指令（解绑命令只走页面）、不做多群 / 群与模块绑定、不做投递重试界面的管理员控制台。
- 机器人凭据仍只由 [ADR-070](ADR-070.md) 的单行配置管理；本 ADR 不引入新的 Secret。

## 5. 后果与验收

- 验收：`permissions:check` 118 / 118；`contract:validate` 118 条；真实 PostgreSQL 集成测试覆盖三态、签发 / 覆盖重签、兑换（成功 / 换绑 / 同群幂等 / 管理员豁免 / PWG01～PWG08）、解绑与幂等重放、授权探针（runtime 无 DELETE）、`purge_project` 清理新表；Web 单测覆盖卡片三态与组长 / 管理员 / 成员可见性；E2E 与开发日志记录见测试矩阵 WECOM-GROUP 小节。
- 后果：项目侧从此有稳定的群绑定标识（`project_wecom_groups`），个人绑定与群绑定相互独立，解绑不清除任何投递历史；桥接改造只需要数据库访问与既有长连接。
