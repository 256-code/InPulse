# ADR-046：三层列表排序统一为「档位优先 + 创建时间从近到远」

- 状态：Accepted
- 基线固化：2026-09-24
- 接受依据：用户 2026-09-24 明确要求「项目排序首先大体按照状态，进行中，未开始，维护中，细化按照创建时间排序。模块和功能按照创建时间从近到远」。
- 修订：修订 [ADR-044](ADR-044.md) 决策第 5 条中「模块列表…组内按 `sort_order`、`id` 升序」的表述。档位定义本身不变：项目档位仍读存储状态（[ADR-043](ADR-043.md)），模块与功能档位仍由已完成任务数派生（ADR-044 / [ADR-045](ADR-045.md)）。
- 修订（2026-10-08）：用户要求「把同状态的项目根据最近的变更排序，最新变更的放在前面，变更指的是生成任务，完成任务等变更」，决策 1 的项目列表第二排序键由 `created_at DESC` 改为「最近变更时间 DESC」（同值再按 `created_at DESC`、`id DESC` 兜底），详见文末「2026-10-08 修订」；档位顺序与模块 / 功能列表不变。

## 背景

1. 三层列表原本的次级排序键不统一：项目按 `id` 升序，模块按 `sort_order`、`id` 升序，功能按 `id` 升序。三处都等价于「最早建的排最前」，新建对象总是沉到列表底部；项目表与模块表的 `id` 顺序也未必等于创建时间顺序，借用主键表达「创建时间」并不准确。
2. `app.modules.sort_order` 自 `0000_initial` 起存在，但应用代码从不写入：`ModuleManagementRepository.create` 的 INSERT 不含该列，模块只有名称与描述可改（ADR-044），前端也没有排序 UI。因此应用内创建的模块恒为默认值 `0`，这条排序键只对演示种子数据有意义（`database/seed/demo-data.sql` 给项目 1 的 8 个模块写了 1~8）。

## 决策

### 1. 三层列表统一为「档位优先 + 创建时间从近到远」

| 列表 | 排序键                                                                                                       |
| --- | --- |
| 项目 | 生命周期档位（`ACTIVE` 进行中 → `NOT_STARTED` 未开始 → `MAINTENANCE` 维护中）→ `created_at DESC` → `id DESC` |
| 模块 | 派生档位（进行中 → 未开始）→ `created_at DESC` → `id DESC`                                                   |
| 功能 | 派生档位（进行中 → 未开始）→ `created_at DESC` → `id DESC`                                                   |

`created_at` 相同时用 `id DESC` 兜底，保证顺序稳定：演示种子数据里项目 1 的 8 个模块创建时间完全相同，缺这一级时数据库可以返回任意顺序。

### 2. 模块排序不再使用 `sort_order`

`sort_order` 从模块列表的 `ORDER BY` 中移除；列本身保留（`modules_sort_order_check` 与演示数据填值都不变）。处理方式与 ADR-044 / ADR-045 保留 `archived_at` 一致：迁移不可逆，不做物理删列。

### 3. 不为此新增索引与迁移

`modules_project_order_idx (project_id, sort_order, id)` 保留。新排序的第一键是由相关子查询算出的 `CASE` 表达式，任何索引都无法满足它，因此追加键 `created_at` 的索引也省不掉排序步骤；而 `WHERE project_id = ?` 与 `WHERE project_id = ? AND module_id = ?` 的定位已有 `modules_project_code_unique`、`features_module_id_idx` 等以 `project_id` 打头的索引可用。

### 4. 档位口径与展示不变

本次只改「同档位内怎么排」，不改「档位怎么算」，也不改卡片上的档位徽章文案与配色。

### 5. 非目标

1. 不改任务中心、迭代记录、通知、项目动态与审计等其它列表的排序（任务列表排序见 [ADR-037](ADR-037.md) 与 [ADR-041](ADR-041.md)）。
2. 不引入用户可拖拽或可配置的排序，也不把 `sort_order` 暴露为可写字段。
3. 不为三层列表新增分页或游标（仍是全量返回）。

## 影响与验证

- 后端：`postgres-project-query-port.ts` 的 `list`、`module-management.repository.ts` 与 `feature-management.repository.ts` 的列表查询三处 `ORDER BY`；`stats/card-stat-columns.ts` 的 `projectLifecycleRankExpression` 与 `lifecycleRankExpression` 补上追加键说明（档位表达式本身不变）。
- 契约与生成物：`route-registry.ts` 的 `listProjects`、`module-routes.ts` 的 `listModules`、`feature-routes.ts` 的 `listFeatures` 描述同步（顺带清掉 `listProjects` 描述里残留的「包含归档历史 / 已归档档位 / 待审归档申请摘要」过时文案）；重生成 `openapi.json`、路由指纹与前端生成客户端，`pnpm contract:drift` 与 `pnpm contract:validate`（98 条路由）通过。
- 测试：`modules-api.integration.test.ts` 两处列表顺序断言改为新键（同属「未开始」档时后建的模块在前）；`projects-read-api.integration.test.ts` 与 `features-api.integration.test.ts` 的同档位用例各新增一个「同档但创建更晚」的对象，断言它排在同档更早对象之前。
- 未运行 / 已知偏差：GitHub Actions 未执行。

## 2026-10-08 修订：项目列表同状态内按「最近变更时间」从近到远

用户 2026-10-08 指示（原话）：「把同状态的项目根据最近的变更排序，最新变更的放在前面，变更指的是生成任务，完成任务等变更」。

- 排序键：项目列表第二键由 `created_at DESC` 改为**最近变更时间 DESC**，其后仍是 `created_at DESC`、`id DESC` 兜底；第一键（生命周期档位：进行中 → 未开始 → 维护中）与档位口径不变，模块与功能列表（决策 1 表格其余两行）不变。
- 「最近变更时间」定义：`MAX(app.activity_projection.occurred_at) WHERE project_id = p.id`，即该项目动态里最新一条业务事件的发生时间；没有动态的项目回落 `p.created_at`。选择理由：项目动态与业务写入同事务落库，生成任务、完成任务、状态流转、发布 / 作废记录、成员变化等都会写进来；而 `projects.updated_at` / `row_version` 只在项目行自身被改动时变化，生成与完成任务不会触碰它。
- 实现位置：`apps/api/src/stats/card-stat-columns.ts` 新增 `projectLastChangeExpression`，由 `postgres-project-query-port.ts` 的 `list` 写入 `ORDER BY`；`projectLifecycleRankExpression` 的注释同步。
- 不为此新增索引与迁移（延续决策 3 的结论）：逐项目 `MAX(occurred_at)` 走既有 `activity_projection_project_cursor_idx (project_id, occurred_at, id)` 的反向索引扫描，排序首键仍是相关子查询算出的 `CASE`，索引无法消除排序步骤。
- 契约与生成物：`listProjects` 的 Route Registry summary 同步；重生成 OpenAPI、路由指纹与前端生成客户端。
- 测试：`projects-read-api.integration.test.ts` 新增真实 PostgreSQL 用例（无动态时回落创建时间、先建项目写入较新动态后跃到前面、后建项目再写更新动态后反超、把先建项目置为进行中后档位仍压过动态时间）；既有档位用例保持不变（夹具无动态，走创建时间回落）。
