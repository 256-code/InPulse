# ADR-025：V1 采用 PGroonga 实现 PostgreSQL 中文与标识符搜索

- 状态：Accepted
- 基线固化：2026-09-07
- 替代：ADR-010

## 背景

阶段 0 的 `pg_trgm` PoC 未满足参数化中文短查询默认使用 GIN 索引的门禁。
候选验证表明，PGroonga 的默认全文 opclass 在 V1 搜索范围内满足中文短词、
完整英文缩写、完整代码标识符和完整编号搜索，并能在 101000 行仿真数据上
使用 PGroonga 索引。

## 决策

V1 搜索仅要求支持中文短词、完整英文缩写、完整代码标识符和完整编号，
不将任意英文/代码子串搜索作为 V1 门禁，也不提供正则表达式搜索。

经 PoC 验证，默认 `pgroonga_text_full_text_search_ops_v2` 在 15 组 V1
语义探针中全部通过，90 条冻结金标 Recall@20 为 100%，跨项目隔离、特殊
输入和边界输入均通过。

因此，V1 采用 PGroonga 作为搜索索引实现，普通搜索使用：

```sql
normalized_search_text &@~ app.pgroonga_query_escape($1)
```

正式实现采用版本化 bootstrap 与显式迁移。PGroonga 不是 trusted extension，
因此实际安装必须在 `database/bootstrap/020_pgroonga.sql` 中由
`cluster_bootstrap` 完成；`0003_search_pgroonga.sql` 保留幂等守卫和
schema 限定的索引：

```sql
CREATE EXTENSION IF NOT EXISTS pgroonga WITH SCHEMA app;
CREATE INDEX IF NOT EXISTS idx_search_projection_pgroonga
  ON app.search_projection
  USING pgroonga (
    normalized_search_text app.pgroonga_text_full_text_search_ops_v2
  );
```

旧 `0001` 的 `pg_trgm` GIN 索引不随 `0003` 删除。`0004` 在确认 PGroonga
索引存在后删除旧 GIN 索引；`0005` 在确认旧 GIN 已删除且 `pg_trgm`
没有扩展外依赖后删除扩展。仓库没有其他使用 `pg_trgm` 的对象，清理证据
由 `pgroonga-migration-report.json`（`version: pgroonga-migration-v3`）
记录，原始 `pg_trgm` 失败 PoC 仍保留为历史证据。

`020_pgroonga.sql` 同时撤销全部 PGroonga 函数对业务角色的 PUBLIC
EXECUTE，只给 `app_runtime` 授权 `pgroonga_query_escape(text)` 与
`&@~` 底层 `pgroonga_query_text(text, text)`，避免运行角色调用
`pgroonga_command` 等管理函数。首次安装只允许 `cluster_bootstrap` 完成，
不授予 `app_migrator`、`app_owner` 或 `app_runtime` 直接
`CREATE EXTENSION pgroonga` 的权限。

V1 不采用未转义的正则查询 `&~`，不使用自定义 TokenNgram 或
TokenBigramSplitSymbolAlphaDigit 作为正式门禁方案。

如果 V2 要求任意英文/代码子串搜索，再单独评估 TokenNgram、
TokenBigramSplitSymbolAlphaDigit 或独立搜索引擎，不影响 V1 决策。

## 影响与验证

- PostgreSQL 18.6 探针镜像已通过 PGroonga 构建、扩展安装和索引可用验证；
  生产多阶段镜像及其最终 digest、Compose 仍由部署纵切片负责。
- `020_pgroonga.sql` 与 `0003-0005` 已落地，并通过真实 PostgreSQL 的
  扩展存在性、opclass、索引、`pg_trgm` contract 清理、runtime 查询/转义
  和管理函数拒绝测试；F-26 的 SearchQueryService 与 API 仍未实现。
- 所有普通搜索输入必须经过 `app.pgroonga_query_escape()`；禁止直接使用
  未转义 `&~` 或透传 Groonga 高级查询语法。
- 默认 `enable_seqscan = on` 下必须使用参数化查询和 PGroonga 索引；
  `enable_seqscan = off` 只能作为诊断手段，不能作为生产配置。
- 逻辑恢复后已验证扩展、索引、权限和默认查询计划可用；生产加密备份、
  签名、异机保留、RPO/RTO 和旧 Session 失效仍由 ADR-020/F-10 验收。
- `0000-0002 -> 0003-0005` 升级和 `0003-0005` 逐迁移事务内回滚已在本地
  验证；生产升级与回滚编排仍需 Runbook 与人工评审。
