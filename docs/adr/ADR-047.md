# ADR-047：迭代记录发布与任务完成解耦

- 状态：Accepted
- 基线固化：2026-09-28
- 接受依据：用户 2026-09-28 明确要求「迭代记录只是记录一下迭代情况，不需要和任务完成挂钩，没有迭代记录也可以点击完成任务」。
- 修订关系：修订[功能设计](../../功能设计v1.1.md) F-18「来源为空或锁内确认来源任务 DONE」与 F-19「完成任务并发布记录」之间的耦合口径，以及[技术设计](../../技术设计v1.2.2.md) §6.3「`task_id IS NULL` 或关联任务为 `DONE` 才能发布」的段落。[ADR-024](ADR-024.md) 的记录状态机不变；F-19 的完成任务并发布记录流程保留，只是不再是从任务侧产生正式记录的唯一入口。

## 背景

1. 解耦前，正式迭代记录只有两条产生路径：无来源任务的独立草稿直接发布（`task_id IS NULL`），或者走「完成任务并发布记录」——在完成任务、写完成信息与状态历史的同一个事务里发布记录。来源任务不是 `DONE` 时，`POST /change-records/{recordId}/publish` 返回 409 `RECORD_SOURCE_NOT_DONE`，提示语为「来源任务尚未完成，请使用发布并完成流程」。
2. 这条门禁建立在「记录是任务完成动作的产物」这一假定上：技术设计 §6.3 明确「发布与完成并发时必须串行并重查，不得提交『已发布记录关联未完成任务』」。但功能设计里记录本身的定义是「一个任务可以没有记录，也可以产生多条记录」——记录描述的是这次迭代做了什么，不是任务被关闭这件事的凭据。
3. 绑定的直接后果是任务侧的「记录一次迭代」只能存草稿：写好了内容却必须先完成（或取消后重开）任务才能发布，与「先记录、再决定是否收尾」「记录与任务状态各自由负责人维护」的用法冲突。
4. 用户据此定案两者解耦，并确认「没有迭代记录也可以点击完成任务」——后者本来已经成立（F-19 的「没有，仅完成任务」分支），不需要新决策。

## 决策

### 1. 发布不再以来源任务的完成状态为门禁

`RecordPublicationAccess.prepare` 删除 `RECORD_SOURCE_NOT_DONE` 分支：来源任务为 `TODO`、`CANCELED`、`DONE` 都能发布关联记录。`RECORD_SOURCE_NOT_DONE` 错误码随之整体下线（Route Registry 与权限矩阵都没有单独登记该码，无需额外收缩）。

### 2. 发布与完成互不写对方的状态

- 发布被拒绝的条件只剩：记录不是 `DRAFT`（409 `RECORD_ALREADY_PUBLISHED`）、归属或来源在锁内发生变化（409 `RECORD_SCOPE_CONFLICT`）、记录或来源任务不可访问（404）。发布**不写** `tasks.work_status`、完成信息与 `task_status_history`。
- 完成任务继续允许不带记录（`COMPLETE/WITHOUT_RECORD`），也继续允许新建或选用已有草稿在同事务内发布。

### 3. 锁序与归属校验全部保留

发布仍然先预读 `change_records.task_id`，再按「任务 → 记录」顺序锁关联任务与记录，并在锁内重查 `task_id`、`moduleId`、`featureId` 与 `impactFeatureIds`：来源任务被并发修改时整段重试，变化后不一致时返回 409 `RECORD_SCOPE_CONFLICT`。发布通知收件人仍包含来源任务当前负责人。解耦只去掉「完成状态」这一个判定，不动同项目归属、父级可写与通知集合。

### 4. 任务侧的记录弹窗与迭代记录页对齐

任务详情「迭代记录」标签页的「记录一次迭代」弹窗与 `/records` 的新建弹窗共用同一实现：归属（所属项目 / 所属模块 / 记录范围 / 影响功能）按来源快照只读呈现，页脚为淡蓝「保存草稿」+ 主按钮「发布迭代记录」；来源任务默认就是当前任务，发布成功后刷新本任务记录列表与任务标记（`task-marks`）计数，任务状态保持不变。

### 5. 非目标

- 不改 [ADR-024](ADR-024.md) 的记录作废与恢复状态机；
- 不移除「完成任务并发布记录」流程，也不因为已有正式记录而阻止完成任务；
- 不建立反向耦合（发布记录不会自动完成任务）。
