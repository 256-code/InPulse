# ADR-047：项目组长唯一性与转移（组长本人可转交身份）

- 状态：Accepted
- 基线固化：2026-09-28
- 接受依据：用户 2026-09-28 连续三条指示——「我要求只剩最后一个成员的时候他就是组长，且不能被移除，除非有其他的成员进来，一个项目至少得有一个成员」，随后撤回初始的「最后一名成员自动继任组长」方案（「还是改成需要先转移才能进行移除」），并追加「然后组长应该也有转移身份的权限」。
- 修订关系：修订 [ADR-039](ADR-039.md) 决策 3、4、5 中「组长转移/撤销仅系统管理员可为」「`roleSetterRole` 仅当 `SYSTEM_ADMIN` 时放行」的授权口径，并强化 [ADR-033](ADR-033.md) / ADR-039 的「每项目**至多**一名 ACTIVE 组长」为「**有活跃成员则恰好**一名 ACTIVE 组长」。ADR-039 的其余决策（取消 `PROJECT_ADMIN`、项目内管理权限下放给全体活跃成员）不变。

## 背景

1. ADR-033 的组长不变量只有一半：`project_members_one_leader` 是部分唯一索引，只能阻止「两名组长」，不能阻止「零名组长」；而 `setProjectMemberRole` 当时允许把唯一组长撤销为 `MEMBER`。结果是项目可以退化成「有成员但没有组长」，没有任何角色为项目负责。
2. 同时没有任何规则阻止移除最后一名成员，项目可以退化成零成员。
3. 初始方案（方案 B「最后一名成员自动继任组长、其余情况禁止移除」）已在实现前被用户撤回：自动继任把「移除」隐式变成「组长替换」，行为不可预测，也不符合「组长代表一个明确的人」的语义。
4. 现行方案（方案 A，本 ADR 固化）：组长只能通过**转移**更换。要移除当前组长，必须先把其他活跃成员设为组长；新组长产生时旧组长自动降级为普通成员，随后即可移除。因此「最后一个成员不能被移除」是两条规则的推论，不需要额外的成员数保护：「唯一活跃成员必然是组长」+「组长不可被移除」⇒ 唯一成员移不动；只有在新成员加入（不再唯一）后，原组长才能通过先转移再移除离开。

## 决策

### 1. 数据库不变量：有活跃成员 ⇒ 恰好一名 ACTIVE 组长

迁移 `0026_project_leader_invariant.sql`：

1. 回填存量「有活跃成员但没有活跃组长」的项目：优先任命**仍然在任的创建者**，否则任命最早加入（`joined_at`、`id` 升序）的活跃成员。回填只解决历史数据，运行期不存在自动继任。
2. `SET CONSTRAINTS ALL IMMEDIATE` 结算上一步产生的延迟约束事件，随后才创建新触发器（顺序不可颠倒，否则 `SET CONSTRAINTS ALL IMMEDIATE` 会连带结算新触发器的事件并提前报错）。
3. `app.assert_project_leader(project_key)`：`SECURITY DEFINER` + `SET search_path = pg_catalog, app`，镜像 `app.assert_project_bootstrap` 的写法——项目行不存在直接返回（级联删除与夹具清理不被拦截）；活跃成员数为 0 直接返回；活跃组长数 ≠ 1 时抛 `check_violation`。
4. `app.check_project_leader_trigger()` + `CONSTRAINT TRIGGER project_members_leader_complete AFTER INSERT OR UPDATE OR DELETE ON app.project_members DEFERRABLE INITIALLY DEFERRED FOR EACH ROW`。
5. 迁移内 `DO` 块自校验回填结果，失败即整体回滚。

**必须用延迟约束**：转移组长要「先把原组长降级、再把新组长提升」两步（`project_members_one_leader` 是不可延迟的部分唯一索引，反向顺序会撞索引），事务中途必然处于「零组长」的中间态。

### 2. 组长不可被移除、不可被撤销

- `removeProjectMember`：目标为 ACTIVE `LEADER` → 409 `PROJECT_MEMBER_LEADER_PROTECTED`（系统管理员同样受限，行为与 ADR-039 一致）。
- `setProjectMemberRole`：把 ACTIVE `LEADER` 改为 `MEMBER` → 409 `PROJECT_MEMBER_LEADER_REQUIRED`「项目必须保留一名组长，请先把其他成员设为组长（转移）」。**「撤销组长」这条路整体取消**，没有「降级后再指定」的可选路径。

### 3. 组长本人可转交身份（修订 ADR-039 决策 4）

`ProjectRoleGateService.roleSetterRole` 返回 `SYSTEM_ADMIN | LEADER | MEMBER | NOT_MEMBER` 四态，判定规则：

| 调用者 | 放行条件 | 否则 |
| --- | --- | --- |
| `SYSTEM_ADMIN` | 任意活跃成员设为 `LEADER` 或非组长成员设为 `MEMBER` | — |
| `LEADER` | 仅当请求 `role = LEADER` 且目标用户不是自己 | 403 `PROJECT_MEMBER_ROLE_FORBIDDEN`「项目组长只能把其他活跃成员设为组长来转移身份」 |
| `MEMBER` | 不放行 | 403「只有系统管理员或本项目组长可以任命组长」 |
| `NOT_MEMBER` | 不放行 | 404 |

- 组长把 `LEADER` 指向自己 → 403：转移必须是「交出去」，避免前端把「设置角色」当成可重复确认的幂等操作。
- 目标成员必须存在且为 `ACTIVE`，否则 404（不泄露成员存在性）。
- 唯一索引冲突（如两个并发转移）→ 409 `PROJECT_MEMBER_LEADER_CONFLICT`。

### 4. 无组长的项目：首位加入者直接成为组长

`addProjectMember` 在项目没有 ACTIVE 组长时（只可能来自历史数据、夹具清理或升级前的存量）把新成员直接写成 `LEADER`（`resolveJoiningRole`），保证「有成员就必须有组长」在写入路径上立即成立，否则该 INSERT 会被延迟约束在提交时拒绝。

### 5. 零活跃成员的项目在数据库层保持合法

- 理由：数据库中「成员集合为空」是删除路径的中间状态——夹具清理需要把成员关系标记 `REMOVED`（`app.assert_project_bootstrap` 只要求创建者的成员行不被**物理删除**，不要求它保持 `ACTIVE`），历史数据也可能如此。数据库无法区分「正当清空」与「意外失去全部成员」，因此不变量只约束非空集合。
- 「一个项目至少得有一个成员」由服务端命令保证：最后一名成员必然是组长（决策 1），组长移不动（决策 2），因此任何命令都无法把项目清空；已清空的项目只有靠 `addProjectMember` 重新获得成员。

### 6. 不新增成员数错误码

方案 A 下「移除最后一名成员」不可达，新增 `PROJECT_MEMBER_LAST_MEMBER_PROTECTED` 只会成为死代码。若将来重新引入自动继任或允许移除组长，必须新增 ADR 并同时补该错误码与门禁测试。

### 7. 幂等契约版本

- `setProjectMemberRole`：`idempotencyContractVersion` 由 `2.1.0` 升到 `2.2.0`。授权语义发生变化（同一请求对组长由 403 变为放行），按 ADR-039 决策 6 的先例升级版本，旧 Key 在新契约下 409。
- `addProjectMember`（`1.2.0`）与 `removeProjectMember`（`1.3.0`）：请求 Schema、响应 Schema、`idempotencyReplayPolicy` 的状态码与可重放字段集合、`replayAuthorizationPolicy` 的资源引用均未变，故版本保持；变化仅限错误文案与「无组长项目首位加入者成为组长」的结果语义。

### 8. 非目标

1. 不做「最后一名成员自动继任组长」，也不允许在项目只剩一名成员时删除该成员或整个项目。
2. 不恢复 `PROJECT_ADMIN`，不给普通成员任命权（ADR-039 的权限下放只针对资源管理，不含角色任命）。
3. 不新增「组长上限」「组长任期」或前端拖拽式角色管理。
4. 不为并发竞态新增数据库重试或进程内锁（见「已知偏差」）。

- **前端**：`ProjectMembersPageView` 新增 `viewerRole` prop（`MEMBER | LEADER | null`）——系统管理员显示「设置角色」，组长显示「转移组长」（只含组长选项），普通成员既不能任命也不受影响；组长卡片不显示移除按钮与角色入口；`project-member-query.ts` 映射 `PROJECT_MEMBER_LEADER_REQUIRED` / `..._PROTECTED` / `..._CONFLICT` 三个 409。
