# ADR-023：一次性认证安全流程的幂等例外

- 状态：Accepted
- 基线固化：2026-09-04

## 背景

登录、CSRF 签发、MFA 注册或验证、恢复码轮换或消费会签发或消费只返回一次的 Cookie、CSRF Token、MFA Secret、验证码状态或恢复码。把这些值写入通用幂等响应表会扩大 Secret 暴露面；只保存 Hash 又无法安全重放完整响应。匿名流程也没有可用于通用唯一键的 `actor_id`。

## 决策

Route Registry 增加显式 `securityFlow` 策略，只允许下表 operationId；路径由阶段 0 的 Route Registry 固化，但 operationId 不得换名规避 allowlist。管理员重置 MFA、修改用户或其他不返回一次性 Secret 的写操作仍使用 `idempotencyRequired`。新增 `securityFlow` operationId 必须通过新 ADR，不能只改 allowlist。

| operationId | 单次消费或自然幂等机制 | 响应丢失后的客户端恢复路径 |
|---|---|---|
| `issueCsrfToken` | 每次签发新 Token，数据库只保存 Hash | 再次签发 |
| `login` | 仅匿名预认证 Session 可调用；原子消费预认证 Session 与 CSRF Hash | 若已有认证/受限 Session，先登出或清 Cookie；重新签发预认证 CSRF 并登录 |
| `logout` | 有效 Session 先验证 CSRF 再条件撤销；无效/已撤销 Session 仅同源清 Cookie | 直接重试，统一返回 204 |
| `startMfaEnrollment` | 按 user → factor → Session 锁序条件递增用户级 enrollment generation；同一旧 generation 只允许一个请求创建新 pending Secret | 重新登录读取当前 generation 后开始注册 |
| `confirmMfaEnrollment` | 按相同锁序校验 expected generation，条件接受对应 pending Secret 的 TOTP time-step，启用因子并轮换为完整 Session/新 CSRF | 清 Cookie 后重新登录；若因子已启用，再重认证并轮换恢复码 |
| `verifyMfa` | 条件接受 TOTP time-step 并升级受限 Session | 重新登录并验证 |
| `reauthenticateAdmin` | 条件接受密码与当前 TOTP，以同一事务时间原子更新 Session 的 `reauthenticated_at` 与 `mfa_verified_at`，并签发服务端一次性 rotation generation | 下一 time-step 重新认证 |
| `rotateMfaRecoveryCodes` | 条件消费该次重认证的 rotation generation，原子失效旧 Hash 并签发新码；同一 generation 只允许一个 2xx | 下一 time-step 重新认证后再次轮换 |
| `consumeMfaRecoveryCode` | 原子消费代码 Hash 并失效旧代码集 | 由另一管理员重置；单管理员走双人离线恢复 Runbook |

`securityFlow` 不接受业务 Idempotency-Key，也不创建 `idempotency_records`。全部用户级 MFA 状态变更统一按 user → TOTP factor → current Session 取锁；factor 不存在时先锁 user 再插入，任何路径不得先锁 Session 再回锁 factor。各操作采用与其语义匹配的机制：同一 preauth+CSRF 只可成功登录一次；MFA enrollment generation 保存于用户唯一的 factor 行而非 Session，start 与 confirm 执行 expected-generation 条件更新，覆盖不同受限 Session，start-vs-confirm 的失败方返回 409，不能用旧 Secret 激活或用新 pending 覆盖 ACTIVE 因子；confirm 成功时在同一事务启用因子、签发恢复码、撤销受限 Session，并轮换为显式 `AUTHENTICATED` Session 与新 CSRF。恢复码轮换条件消费 Session 的 rotation generation，同一旧 generation 的竞争者返回 409；MFA 验证、管理员重认证与恢复码消费通过条件更新保证对应验证 Session、TOTP time-step 或恢复码只被接受一次；`issueCsrfToken` 可以重复签发；登出在有效 Session 下验证 CSRF 并撤销，Session 无效或已撤销时仅在同源 Origin/Referer 与 Fetch Metadata 通过后清 Cookie、返回 204 且不执行状态写。通用或专用持久化均不得保存可重放的 Cookie、CSRF 明文、MFA Secret、验证码或恢复码明文。

响应丢失时客户端必须开始新的安全流程：CSRF 签发可直接重签；登录/验证类流程清理不确定 Cookie 后重新登录；`startMfaEnrollment` 响应丢失时重新登录读取当前 enrollment generation，使旧 pending 失效并重新开始；`confirmMfaEnrollment` 可能已经提交并把 factor 置为 ACTIVE，此时重新登录完成 MFA，再于下一 TOTP time-step 重认证并轮换恢复码；恢复码首次展示丢失时同样取得新 rotation generation，生成一组新码并原子失效旧 Hash。服务端不得尝试从 Hash 恢复旧明文。

每个 operationId 的可调用主体、受限 Session/challenge 前置状态、停用用户结果及拒绝用例以[权限矩阵](../permissions.md)的“认证安全流程矩阵”为权威基线；不得用一条笼统“登录”权限覆盖替代逐操作映射。

## 影响与验证

Route Registry CI 必须断言 `securityFlow` operationId 集合与上表精确相等，并拒绝缺少 `idempotencyExceptionAdr: ADR-023`、单次消费/自然幂等机制或客户端恢复说明的条目；`issueCsrfToken` 不能按普通 GET 登记为 `none`。真实 PostgreSQL 并发测试按 operationId 验证：同一 preauth+CSRF 只成功登录一次；用户级 enrollment generation 的 start-vs-start、start-vs-confirm 及跨 Session 竞争只有一个条件更新成功；同一 rotation generation、验证 Session、TOTP time-step 或恢复码只被相应消费操作接受一次，竞争者为 409；确认注册不会停留在受限态且旧 Session/CSRF 已失效；重复 CSRF 签发均可成功；重复登出均为 204，且无效 Session 分支只清 Cookie。管理员重认证还要断言两个新鲜度时间戳原子同值刷新；日志、审计、数据库与幂等表扫描不得出现上述 Secret 明文。客户端 E2E 覆盖每条响应丢失后的恢复路径。
