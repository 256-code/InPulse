# ADR-044：模块层面下线归档，模块只有 ACTIVE

- 状态：Accepted
- 基线固化：2026-09-23
- 接受依据：用户 2026-09-23 明确要求「接下来我们改模块的归档，直接去掉这个功能」（模块页 `/projects/{projectId}/modules`）。
- 替代：替代 [ADR-034](ADR-034.md) 中**模块归档与恢复**的全部决策（`archiveModule` / `restoreModule`、409 `MODULE_ARCHIVE_TASKS_OPEN`、`FEATURE_MODULE_ARCHIVED`）；ADR-034 中功能归档、任务归档与父级归档前置校验继续有效（功能层 `parent-not-active` 保留）。
- 修订：修订 [ADR-033](ADR-033.md) 与 [ADR-039](ADR-039.md) 中「模块归档 / 恢复授权给项目内成员」的口径——该授权对象随路由下线一并消失。

## 背景

1. 模块归档落地后没有形成真实使用场景：模块是项目内长期存在的分类容器，功能与任务才是会被收尾的对象；把一个模块标成「已归档」只换来一个只读态，团队既不会因此少看一个模块，也不会因此收回任何权限。
2. 归档同时带来一整套连带复杂度：模块写入口要先判断父级是否归档（`ModuleQueryPort.checkModuleForWrite` 的 `parent-not-active`），模块下所有写路径（功能、任务、迭代记录、遗留项、外部链接、聚合组、任务完成 Workflow）都要跟着维护「模块已归档」分支，并且还要额外定义「模块归档要求模块下任务全部收尾」这一档门禁（409 `MODULE_ARCHIVE_TASKS_OPEN`）。
3. 与项目侧同理（[ADR-043](ADR-043.md)）：真正需要「不排期但仍可用」的档位在项目层由「维护中」承担，模块层没有对应语义，因此模块不再是生命周期资源。
4. 功能、任务、迭代记录与遗留项的归档仍然有真实语义（「从活跃视图移除但保留历史」），本次不动。

## 决策

### 1. 模块状态只有 `ACTIVE`

数据库 `modules_status_check` 收紧为 `CHECK (status = 'ACTIVE')`；`archived_at` 列保留为只读历史列但恒为空，由 `modules_archived_at_null_check CHECK (archived_at IS NULL)` 兜底（迁移不可逆，不做物理删列）。迁移 `0024_module_archive_removal.sql` 负责升级窗口：先摘除 `modules_archive_state_check`，再在临时关闭 `modules_row_version` 触发器的情况下把存量 `ARCHIVED` 行回填为 `ACTIVE` 并清空 `archived_at`（不递增 `row_version`），最后收紧状态 CHECK 并新增兜底约束。历史迁移不改写。

### 2. 两条归档路由与原因 Schema 整体下线

- 路由：`archiveModule`、`restoreModule` 从 Schema Registry、Route Registry、权限矩阵、OpenAPI 与生成客户端移除（Route Registry 102 → 100 条）；
- Schema：`ModuleArchiveRequest`（原因）整体删除，模块不再有「非空原因 + 最多 2000 字」的归档语义；
- DTO：`moduleItemSchema` 去掉 `status` 与 `archivedAt`，`updateModule` 的幂等契约版本由 1.3.0 升到 **1.4.0**（响应 Schema 变化会让旧 Key 在新契约下 409）。

### 3. 模块写前检查收窄为「存在 + 归属」

`ModuleWriteCheckResult` 由 `allowed | not-found | parent-not-active` 收窄为 `allowed | not-found`，`ProjectWriteAccessFailure` 去掉 `module-not-active`；模块侧的 `FEATURE_MODULE_ARCHIVED` 与 `MODULE_ARCHIVE_TASKS_OPEN` 两个错误码一并删除。功能级检查不变：`feature.status = 'ARCHIVED'` 仍返回 `parent-not-active`，功能归档仍要求所属模块存在且归属正确。

### 4. 模块不再有「任务全部收尾」门禁

模块归档要求模块下不存在 `lifecycle_status = 'ACTIVE'` 且 `work_status NOT IN ('DONE','CANCELED')` 的任务，这条门禁随模块归档一起消失；同一「未收尾任务」定义继续由项目侧「进入维护中」使用（409 `PROJECT_MAINTENANCE_TASKS_OPEN`）。

### 5. 模块展示口径：仍是「进行中 / 未开始」两档，顺序与分组不变

模块卡上的档位标签原本就由该模块已完成任务数派生（`stats.completedTaskCount`），与服务端存储状态无关；本次只删掉派生结果的第三档「已归档」。模块列表仍按派生档位分组（进行中在前、未开始在后），组内按 `sort_order`、`id` 升序；功能列表保留「进行中 / 未开始 / 已归档」三档。

### 6. 前端只剩「编辑模块」

模块卡内不再有归档 / 恢复入口，编辑弹层底部只剩「取消 / 保存」，模块页头不再有归档 / 恢复按钮，也不再有「模块已归档」只读提示与禁用态；同理移除移动端归档入口。

### 7. 非目标

1. 不删除功能、任务、迭代记录与遗留项的归档 / 恢复，也不改动它们的父级归档前置校验（功能层 `parent-not-active` 保留）。
2. 不新增模块删除（物理删除）、模块级状态或模块生命周期档位。
3. 不改动 `archiveModuleTask` / `restoreModuleTask` 与 `archiveTask` / `restoreTask`：它们是「模块级任务 / 功能级任务」的归档命令，与模块归档无关，继续有效。
4. 不清理历史审计、历史动态与历史通知中既有的模块归档记录，只保留只读展示。
