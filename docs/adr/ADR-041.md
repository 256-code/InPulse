# ADR-041：原始审计读取留痕按「查看」计数（进入与切换对象各一条）

- 状态：Accepted
- 基线固化：2026-09-23
- 修订关系：修订技术设计 §7 的 `GET /audit-logs` 留痕口径、§11 的读取留痕实现要求与系统设计 §6 的审计读取留痕表述，并同步 `docs/permissions.md` 与 `docs/test-matrix.md` 的对应验收描述。审计链结构、HMAC 哈希链、`audit_reader` 只读连接、签名游标、管理员 Session 与 422 校验语义不变；「留痕失败即整体失败、绝不返回未留痕结果」不变。

## 背景

原口径是「每次原始审计读取都写 `AUDIT_LOG_READ`」，按 HTTP 请求计数。前端审计页进入即读、切换审计链读、应用筛选读、重置筛选读、点「加载更多」读，于是单次人工浏览会连续产生多条留痕。本地实测 SYSTEM 链中 `AUDIT_LOG_READ` 一度累积到 101 条，仅次于登录失败事件，既淹没真实业务事件的可读性，也让「谁在什么时候看过审计」这一取证信息被自身噪声稀释。

## 决策

1. **粒度**：一次「查看」= 进入审计页 + 每次切换审计对象（`SYSTEM` 链 ↔ 各 `PROJECT:<id>` 链）。同一次查看内的筛选、重置、重试与分页不再产生新留痕。
2. **分页由服务端判定**：带签名 `cursor` 的请求是同一次查看的延续，服务端不写留痕，与客户端是否声明无关。这样直接调用 API 的客户端也无法用游标绕过判定。
3. **客户端声明**：请求新增参数 `readTrail`（`"true"` / `"false"`，省略按 `"true"`）。只有开启新查看的请求省略该参数或传 `"true"`；筛选、重置与重试传 `"false"`。用字符串枚举而不是布尔，避免 query 字符串 `"false"` 被误判为真值（`Boolean("false") === true`）；其他取值按 422 拒绝。
4. **留痕内容与失败语义不变**：仍写 SYSTEM 链，仍记录链、filters、`returnedCount`、`hasMore`、操作者与请求元数据，不含审计正文；追加失败仍丢弃结果并整体失败。
5. **无跨请求状态**：判定只依赖请求本身，不引入服务端会话、内存计数器或时间窗去抖，避免多实例下的行为漂移。
6. **明确不做**：不做同一管理员连续切换的时间窗合并、不记录翻页次数或阅读深度、不新增独立访问链。需要逐次取证时按 F-08 步骤 6 的远端 WORM 归档与加密明细导出处理。

## 影响与验证

- 契约：`auditLogQueryRequestSchema` 新增 `readTrail`，Route Registry 的 `getAuditLogs` 摘要同步改写；`pnpm contract:drift`（5 个产物）、`contract:validate`（108 条路由）、`permissions:check`（108/108）通过。
- 后端：`AuditQueryService.query` 以 `query.cursor === undefined && query.readTrail !== "false"` 判定是否写留痕。
- 前端：`useAuditLogsInfiniteQuery` 增加 `readTrail` 选项（默认 `true`），分页请求固定携带 `readTrail=false`；审计页在进入与切换审计链时置 `true`，筛选与重置置 `false`。
- 测试：真实 PostgreSQL 集成新增「筛选与分页不写新留痕、新查看恰写一条、非法 `readTrail` 返回 422」用例（`apps/api/test/audit-logs.integration.test.ts` 7/7）；Web 单测断言分页与筛选携带 `readTrail=false`、首屏与切链不携带该参数（85 文件 579 例通过）。
- 代价：同一次查看内的阅读深度（翻页次数）不再进入审计链；补偿性取证依赖 WORM 归档的访问明细，需要在运维层面按需导出。
