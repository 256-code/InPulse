# ADR-041：删除任务优先级的「低」（LOW）档位

- 状态：Accepted
- 基线固化：2026-09-23
- 接受依据：用户 2026-09-23 明确要求「取消低优先级，彻底删除所有和低优先级有关的代码 UI」。
- 修订关系：修订 [ADR-037](ADR-037.md) 的任务列表排序键——优先级序号由 0/1/2/3 收窄为 0/1/2，游标版本 3 → 4。ADR-037 的状态分组、紧急桶、完成时间倒序与多列 keyset 结构均不变；F-14/F-16/F-32 的任务字段集合也不变，只是把 `priority` 的取值域收窄一档。

## 背景

1. `app.tasks.priority` 自初始迁移起就是四档 `LOW / NORMAL / HIGH / URGENT`（`tasks_priority_check`，默认 `NORMAL`）。
2. 「低」档位在实际使用中没有形成业务价值：2026-09-21～09-22 的卡片配色定案里，「低」已经等于「不铺实色」的中性白底卡，与「已取消」的浅灰底在同屏上几乎分不出来；它反而让优先级筛选、创建/编辑表单、任务看板筛选与卡片配色都多出一档没有语义的噪声。
3. 用户因此要求彻底删除该档位，包含筛选下拉、创建/编辑表单、看板筛选、卡片配色与数据库约束。

## 决策

1. **数据面**：新增迁移 `0022_drop_low_priority.sql`——先把存量 `LOW` 行归一到默认档 `NORMAL`（按行版本触发器要求同时 `row_version = row_version + 1`），再 `DROP`/`ADD` 把 `tasks_priority_check` 收紧为 `NORMAL / HIGH / URGENT`。历史迁移 `0000_initial.sql` 不改写，升级窗口由该新迁移承接。
2. **不物理删除**：归一只是降级，任务本体、状态历史、审计链、活动与搜索投影、聚合关系全部保留；存量 `LOW` 任务的编号与内容不变。
3. **契约面**：`TASK_PRIORITIES`、`TaskEditRequest.priority`、`ProjectMemberUnfinishedTaskItem.priority`、`TaskBoardCard.priority` 的枚举同步收窄为三档；OpenAPI 与生成客户端只由生成工具更新，禁止手改。请求里出现 `LOW` 一律 422 `VALIDATION_FAILED`。
4. **排序与游标**：`task-list-order.ts` 的优先级序号由 `URGENT 0 / HIGH 1 / NORMAL 2 / ELSE 3` 收窄为 `URGENT 0 / HIGH 1 / NORMAL 2 / ELSE 2`；`TASK_LIST_SORT_KEY_VERSION` 由 3 升到 4，旧游标整版拒绝——旧键里的 `3`（原「低」）在新口径下不是任何任务的序号，继续接受会让 keyset 比较静默退化、跳页或漏项。任务看板（`task-query.port.ts` 的 `listForBoard`）走同一套档位。
5. **前端**：删除 `PRIORITY_LABELS.LOW`、`PRIORITY_BADGE_TONES.LOW`、`PRIORITY_DOT_COLORS.LOW`、`priorityOrder` 末项、任务看板与遗留项转任务的 `LOW` 选项、`TasksPanel` / `GlobalTaskCreateModal` 的标签与色调条目，以及 `design-system.css` 里 `.tone-prio-low` 的三处定义。`taskToneOf` 与 `priorityDotColor` 的未知值兜底由「低」改为「普通」（`normal` / `#a0adb9`；同日配色二次定案把白色圆点改判为中性灰，兜底值随之从 `#337ee6` 收紧到 `#a0adb9`）。
6. **演示种子**：`demo-data.sql` 的 3 条任务行改为 `NORMAL`；对应 `task.create` 审计行的事件载荷保留 `"priority": "LOW"`——审计是只追加的不可变历史，改载荷会让哈希链失配，因此不做「事后美化」。
7. **非目标**：不新增、不重命名其它优先级档位；不引入自定义优先级；不改动优先级之外的任何任务字段。
