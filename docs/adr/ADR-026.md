# ADR-026：NestJS 基线锁定 11.2.3 并延后 12.x 升级

- 状态：Accepted
- 基线固化：2026-09-07
- 替代：ADR-003

## 背景

[ADR-003](ADR-003.md) 把 NestJS 11.x 作为候选基线，并要求阶段 0 完成 12.x 兼容性 PoC 后由新增 ADR 决定升级或继续暂留，同时锁定实际补丁版本。该门禁现已执行：以 `apps/api` 现有编译配置（CommonJS、`moduleResolution: Node10`、strict、`experimentalDecorators` 与 `emitDecoratorMetadata`、target ES2024）在仓库外临时目录对 11.2.3 与 12.0.1 做了同源码双变体验证，覆盖类型检查、构建、导出符号、依赖图、运行时契约与安全行为、测试工具链和 ESM 路径。完整证据见 [NestJS 11.x 与 12.x 兼容性 PoC 结果](../poc/nestjs-11-vs-12-v1-result.md)。

版本事实：`@nestjs/common` 11.2.3 发布于 2026-08-25，12.0.0 与 12.0.1 均发布于 2026-08-27；截至 2026-09-07，npm `latest` 为 12.0.1，尚无 12.0.2 或 12.1.x，即 12.x 只有 11 天历史与一个补丁版本。

## 决策

本期 NestJS 基线锁定 11.2.3（`@nestjs/common`、`@nestjs/core`、`@nestjs/platform-express`、`@nestjs/testing`），继续使用默认 Express Adapter，不升级 12.x。本 ADR 替代 ADR-003，并完成 [ADR-017](ADR-017.md) 要求的实际补丁版本锁定：`apps/api/package.json` 与 `pnpm-lock.yaml` 已精确固定 11.2.3，本决策不产生 manifest 或 lockfile 变更。

PoC 证明 12.0.1 与 11.2.3 在本项目关心的路径上行为一致：四个包导出符号无删除，`@nestjs/core`、`@nestjs/platform-express`、`@nestjs/testing` 的依赖集合完全一致，两者都解析 Express 5.2.1 与 path-to-regexp 8.4.2，18 项运行时契约与安全冒烟逐项状态码一致，归一化随机值后 17 项响应逐字段相同，唯一差异是未匹配路由的处理路径（见「影响与验证」），ESM 路径在两个版本上同样可用。Express 5 属于 11.2.3 既有基线，不是 12.x 的迁移成本。因此升级 12.x 不带来本期必需能力，只带来新发布主版本的风险。

继续暂留 11.x 的理由：

1. 12.x 发布仅 11 天且只有一个补丁版本，阶段 0 以稳定优先；
2. 12.x 的原生 Standard Schema Pipe 与 Serializer 是真实收益，但技术设计 4.1 第 11 与 12 项要求的请求校验、响应剔除未知字段、响应契约违规净化为 500 与 422 统一错误体，在 11.2.3 上用自研 Zod Pipe 与序列化拦截器已实测等价满足，不构成功能阻断；
3. 生态尚未跟进：社区 `nestjs-zod@5.5.0` 的 peerDependencies 只声明 `@nestjs/common ^10.0.0 || ^11.0.0`；
4. 12.x 已知代价：未匹配路由回落到 Express 默认 HTML 404；`@nestjs/cli@12.0.0` 的依赖树捆绑 typescript 6.0.3，与仓库 catalog 的 5.9.3 形成双编译器；包内 `exports` map 阻断 `require('@nestjs/*/package.json')`。

本 ADR 只决定 NestJS 主版本与补丁版本，不决定 OpenAPI 生成工具与 Nest Zod Pipe/Serializer 组合；按 `AGENTS.md` 第 4 节，后者仍属未定案项，不得写成已冻结选择。

## 升级触发条件

出现以下任一情况时重新评估 12.x，评估结论必须再新增 ADR：

- 12.x 发布 12.1.0 或更高次版本；
- 12.0.x 自 2026-08-27 起满 90 天（2026-11-25 之后），且期间没有出现影响本项目路径的高危回归或安全公告；
- 11.x 出现影响本项目的安全公告，而修复只存在于 12.x；
- 本项目决定改用原生 Standard Schema Pipe/Serializer 替代自研管道，或需要其他 12.x 独有能力。

升级只能作为独立依赖升级 PR 由人工确认，不得自动合并，也不得与其他功能变更混在同一 PR。

## 升级时必须完成的工作

1. 未匹配路由的契约 404：12.x 下必须在 `app.init()` 之后注册终端中间件输出统一 JSON 404，使用固定文案且不回显 method 与 path，并保留[测试矩阵](../test-matrix.md) `SEC-006` 回归；
2. 构建链继续使用 `tsc`；若引入 `@nestjs/cli@12`，必须把其捆绑的 TypeScript 与仓库 catalog 的 TypeScript 对齐，避免同一份源码由两个编译器产出；
3. 工具链不得 `require('@nestjs/*/package.json')`，改为从磁盘路径读取包元数据；
4. 评估以原生 `StandardSchemaValidationPipe` 与 `StandardSchemaSerializerInterceptor` 替代自研 Zod Pipe 与序列化拦截器；替代必须保持 422 契约体、`details` 字段语义与净化 500 行为，并同步技术设计第 4 章；
5. 复核新增依赖 `@standard-schema/spec@1.1.0` 与 `file-type` 21.3.4 到 22.0.2 的许可证与漏洞扫描；
6. 重跑全部门禁（类型检查、构建、运行时冒烟、单元与集成测试、E2E、真实 PostgreSQL 集成、安全响应头与 CSP）后，才更新 manifest、lockfile 与生产镜像 digest。

## 影响与验证

- 本期请求与响应校验继续使用自研 Zod Pipe 与序列化拦截器：11.2.3 不导出 `StandardSchemaValidationPipe` 与 `StandardSchemaSerializerInterceptor`，PoC 实测两者为 `undefined`。
- 未匹配路由必须在 11.x 上显式修正异常过滤器：11.2.3 虽然返回 JSON 404，但 message 回显 `Cannot GET /api/v1/...`，违反统一错误文案与不得泄露内部细节的要求；11.x 下在 `app.init()` 之后注册终端中间件不生效，异常过滤器先接管，必须直接修正过滤器文案。验收项见[测试矩阵](../test-matrix.md) `SEC-006`。
- ESM-only 第三方包与 `apps/api` 现有 `moduleResolution: Node10` 的矛盾独立于本决策：PoC 中 `cookie@2.0.1`（`type: module` 且仅提供 `exports`）在该配置下报 TS2307，改用 `NodeNext` 才能解析，且 `cookie@2` 已把 `parse` 与 `serialize` 改名为 `parseCookie` 与 `stringifyCookie`。引入此类依赖前必须先决定 moduleResolution 或选用 CJS 版本，不得假设它随 NestJS 版本变化而消失。
- PoC 在仓库外临时目录执行，源码、依赖与产物均未进入仓库，也未改动生产依赖清单；本 ADR 与证据文档是其唯一留存记录。
- 阶段 0 其余门禁不受本决策影响，仍按技术设计第 14 章执行：Drizzle 与 Nginx 实际补丁与镜像 digest、PostgreSQL 18.6 官方基线的 PGroonga 验证（见 [ADR-025](ADR-025.md)）以及其余 CI 门禁。
