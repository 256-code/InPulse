# ADR-027：契约生成链路使用 Zod 4 JSON Schema 与仓库内生成器

- 状态：Proposed
- 提出日期：2026-09-07
- 关联：[ADR-004](ADR-004.md)、[ADR-017](ADR-017.md)、[ADR-019](ADR-019.md)、[ADR-023](ADR-023.md)、[ADR-026](ADR-026.md)
- 性质：本记录是契约生成链路的「定案材料」。转为 `Accepted` 前须通过第 7 节评审清单，并由非作者人工确认（作者不得自批）。

## 背景

[ADR-004](ADR-004.md) 确定 Schema Registry/Zod 与 Route Registry 共同生成 OpenAPI 3.1 与 TypeScript 客户端，技术设计 §12.4 要求每个 PR 通过 OpenAPI/客户端漂移检查与 Route Registry/权限/响应 Schema 完整性检查。`AGENTS.md` 第 4 节把「OpenAPI 生成工具」列为阶段 0 尚未定案项，并禁止在规则或实现中伪装成已冻结选择。

阶段 0 需要真实落库这条链路才能执行上述门禁，因此必须先形成决策记录，而不是让实现默认成为既成事实。当前 `packages/api-contract` 已按本草案落库，本文件把「已实现、已决策」与「仍待定案」清晰分开，供人工评审。

## 决策

1. **JSON Schema 来源**：Schema Registry 的每个条目是 Zod 4（锁定 4.5.4）schema，OpenAPI `components.schemas` 由 Zod 内置 `z.toJSONSchema(..., { io: "output", target: "draft-2020-12" })` 产出，并删除顶层 `$schema`、把 `$defs` 折叠进 `components.schemas`、把根 `$ref` 改写为 `#/components/schemas/...`。不引入独立的 JSON Schema 定义源，避免出现第三份真相。
2. **生成器归属**：OpenAPI 文档与 TypeScript 客户端由仓库内生成器产出（`packages/api-contract/src/json-schema.ts`、`openapi.ts`、`ts-types.ts`、`client.ts`），入口为 `pnpm contract:generate`。本期不把 `@nestjs/swagger`、`openapi-generator`、`orval`、`openapi-typescript` 等第三方生成工具加入生产依赖。
3. **生成物落库与只读性**：`packages/api-contract/generated/openapi.json`、`route-contract-fingerprints.json` 与 `apps/web/src/generated/api/{types,client,index}.ts` 提交入库，只能由生成器写入；`pnpm contract:drift` 逐字节比对生成结果与已提交内容，并拒绝生成目录中出现非生成器产出的文件（`.gitkeep` 豁免）。
4. **Route Registry 是唯一 HTTP 元数据来源**：`packages/api-contract/src/route-registry.ts` 登记 method、path、operationId、状态码、Content-Type、鉴权、CSRF、幂等与并发策略；不适用的策略必须显式写 `none`。`pnpm contract:validate` 校验策略完整性、`idempotencyReplayPolicy`/`replayAuthorizationPolicy` 的字段边界与 Secret 字段禁令（ADR-019/ADR-023），并静态扫描 `apps/api` Controller 绑定：当前实现按 method+path 解析 Nest 装饰器（`@Controller` 与 HTTP 方法装饰器），要求每个已登记路由在 Controller 中恰好有一个匹配端点，同时拒绝未登记到 Registry 的端点。operationId 是契约层标识；运行期是否用自定义操作符把 operationId 绑定到 Controller 端点由第 5 节另行决定。
5. **权限矩阵可执行化**：`packages/api-contract/src/permission-matrix.ts` 是 `docs/permissions.md` 的可执行副本；`pnpm permissions:check` 双向校验二者一致（含身份集合与 ADR-023 认证安全流程矩阵），并要求每条非 `authPolicy: none` 路由至少有一条允许与一条拒绝用例登记。
6. **契约指纹仅用于 CI**：`packages/api-contract/generated/route-contract-fingerprints.json` 记录每个 `idempotencyRequired` operationId 在某个幂等契约版本下的 SHA-256 指纹，历史条目只追加、不重写，用于检测「契约已变更但未升级 `idempotencyContractVersion`」。它是 CI 侧变更探测器，**不是**运行时幂等 fingerprint；运行时仍必须使用带版本密钥的 HMAC-SHA-256（`AGENTS.md` 第 6 节）。
7. **本 ADR 不决定的事项**：Nest Zod Pipe/Serializer 组合与运行参数仍属 `AGENTS.md` 第 4 节未定案项；[ADR-026](ADR-026.md) 已说明本期使用自研 Zod Pipe 与序列化拦截器，其定案仍需独立评审。

## 替代方案与权衡

| 维度 | 已选 | 主要替代方案 | 取舍 |
| --- | --- | --- | --- |
| JSON Schema 来源 | Zod `z.toJSONSchema`（单一真源） | 手写 JSON Schema 作为第三份真相；`@nestjs/swagger` 从 Nest 装饰器生成 | 手写源会与 Zod/契约漂移，违反 ADR-004 单真相；Nest 装饰器源把契约耦合到运行期装饰器，且无法与 Schema Registry 对齐。 |
| 生成器归属 | 仓库内生成器 | openapi-generator / orval / openapi-typescript 等第三方 codegen | 第三方工具需作为 dev 依赖引入、输出形状受工具约束、难以保证「遇到不支持节点即失败」，并可能在客户端引入额外运行时依赖；如后续评估改用，须新增 ADR 替代。 |
| 客户端传输 | 仅原生 `fetch` 的自包含类型化客户端 | axios 等 HTTP 客户端 | 避免额外生产依赖；自包含类型不引入 zod 运行时依赖，客户端校验不能替代服务端校验。 |
| 生成物处理 | 生成物提交入库 + `drift` 逐字节比对 + 拒绝额外文件 | CI 构建时在线生成、不提交 | 提交入库让客户端可脱离构建环境引用、漂移可回归追溯；代价是生成物随 PR 产生噪音，且必须与源定义同 PR 重新生成。 |

## 后果

**正面：**
- 单一真源：Zod Schema Registry + Route Registry 共同决定请求/响应/策略；生成物可回归且禁止手工修改，杜绝几份真相漂移。
- 仓库内生成器确定性高、无第三方运行时依赖；遇到无法表达的节点抛错而非静默降级或退化成 `any`。
- 客户端自包含、仅依赖原生 `fetch`，服务端仍是唯一校验主体。
- 权限矩阵可执行化并在 CI 与文档双向一致；契约漂移、Route Registry 完整性与鉴权/CSRF/幂等策略在 CI 可查。

**代价与风险：**
- 维护自研生成器与 TS 类型打印器的长期成本；随业务 Schema 复杂度增长需持续扩展。
- 生成物提交带来 PR 噪音与潜在合并冲突；契约变更必须同一 PR 重生成并通过漂移检查。
- 依赖 Zod `z.toJSONSchema` 的精确行为，升级 Zod 版本需评估输出变化；Zod 4 锁定 4.5.4。
- 在 `Accepted` 前，该组合不得当作冻结基线，相关实现仍可能调整。

## 本 ADR 未决范围（后续独立决策）

- **Nest Zod Pipe/Serializer 组合与运行参数**：`AGENTS.md` 第 4 节明确仍属未定案项；本 ADR 不决定，也不得在规则或实现中伪装成已冻结。
- **运行期 operationId → Nest 端点绑定**：当前 `contract:validate` 仅按 method+path 匹配 Nest 装饰器；是否引入自定义操作符（如 `@Operation("login")`）并在运行时用 Zod Pipe/Serializer 校验请求/响应，属独立决策。
- **业务域路由契约登记**：搜索、认证、项目等业务路由接入本链路属于对应功能实现；本 ADR 只约定生成/校验机制，不逐条确定这些路由。

## 影响与验证

- 状态为 `Proposed`：实现已按本草案落库以便执行 §12.4 门禁，但在人工评审转为 `Accepted` 前，不得把该组合当作已冻结基线，也不得据此拒绝评估第三方生成工具。
- 转为 `Accepted` 前必须完成的评审项见第 7 节。
- 已实际执行的验证（2026-09-07，Windows / Node 24.20.0 / pnpm 11.19.0）：`pnpm contract:generate` 产出 5 个生成物；`pnpm contract:drift`、`pnpm contract:validate`（1 条路由）、`pnpm permissions:check`（1 条操作 / 1 条路由）与 `pnpm --filter @inpulse/api-contract test:unit`（3 个文件 50 个用例）全部通过；`pnpm lint`、`pnpm typecheck`、`pnpm build` 通过。
- 未实际执行的验证：`.github/workflows/ci.yml` 中的 GitHub Actions 运行本身（本机无 Actions 运行环境）。
- **环境说明**：本材料撰写时，因 sandbox 内 pnpm 需联网校验包管理器签名、tsx 的临时目录机制调用 `os.userInfo()` 返回 ENOMEM，无法在本地重跑上述门禁；上文验证为历史记录，不代表本次会话重新执行。
- 若评审决定改用第三方生成工具，必须新增 ADR 替代本记录，并在同一 PR 中重新生成全部生成物、更新 `AGENTS.md` 第 4/5 节与本文件状态。

## 转为 Accepted 前的评审清单

评审人在把状态改为 `Accepted` 前，须逐项确认：

1. 在具备联网的环境执行 `pnpm install --frozen-lockfile` 后，按技术设计 §12.4 顺序运行 `contract:generate`、`contract:drift`、`contract:validate`、`permissions:check` 与 `@inpulse/api-contract` 单测，全部通过且无漂移；对应 PR 的 `CI / workspace` 通过。
2. 抽查 `openapi.json` 的 draft-2020-12 输出满足 OpenAPI 3.1 子集：`$defs` 已折叠进 `components.schemas`、`$ref` 指向 `#/components/schemas/...`、无 `$schema`；确认没有把非预期节点静默降级。
3. 确认 `ts-types.ts` 遇到不支持节点抛错、`types.ts` 不含 `any`；生成客户端仅依赖原生 `fetch` 与自包含类型，无 axios/zod 运行时依赖。
4. 确认 `Route Registry` 每条路由策略均显式登记；`securityFlow` allowlist 与 ADR-023 精确相等；`idempotencyReplayPolicy`/`replayAuthorizationPolicy` 的字段边界、响应 Schema 一致性与 Secret 字段禁令由 `validate` 覆盖。
5. 确认 `permissions:check` 双向校验 `docs/permissions.md` 与可执行权限矩阵，身份集合与 ADR-023 认证安全流程矩阵一致；`authPolicy: none` 的豁免逻辑未放宽任何业务或认证路由。
6. 确认新增路由时生成物与 Controller 扫描同步；无手工修改生成物、无未登记端点；`pnpm-lock.yaml` 随依赖变更提交。
7. 确认本项目内未把任何第三方 OpenAPI/客户端生成工具加入生产依赖。
8. 非作者人工评审并批准（契约平台作为共享基建可由 B 或 C 评审；如涉及身份/会话/CSRF 相关契约，评审人应为 B），再将状态改为 `Accepted`，并同步把 `AGENTS.md`、`CONTRIBUTING.md`、`README.md` 中仍称 `Proposed` 的表述更新为 `Accepted`。
