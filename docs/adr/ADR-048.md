# ADR-048：迭代记录草稿支持物理删除

- 状态：Accepted
- 基线固化：2026-09-28
- 接受依据：用户 2026-09-28 明确要求「我希望在草稿箱里的迭代记录可以删除，就是点开编辑的时候有删除选项」。
- 修订关系：明确 [ADR-024](ADR-024.md) 记录状态机中 `DRAFT` 一档的删除语义——此前只有 `DRAFT -> PUBLISHED -> VOID` 与管理员 `VOID -> PUBLISHED` 恢复，没有删除入口。本 ADR 不改变 `PUBLISHED` / `VOID` 两档「不可物理删除、只能通过作废与恢复保留历史」的不变量，也不放宽 `app_runtime` 对 `app.change_records` 的表级权限。

## 背景

1. 仓库规则把「业务历史默认通过归档、作废或新版本保留，不物理覆盖或删除」定为不变量。正式迭代记录（`PUBLISHED` / `VOID`）有正式编号、不可变版本、遗留项快照、审计与活动/搜索投影、外部链接关联，物理删除会同时破坏多处引用与历史可读性。
2. 草稿（`status = 'DRAFT'`）不具备上述任何一项：没有正式编号（`code` 为空）、`current_version = 0` 且 `assert_change_record_versions` 触发器要求草稿没有版本行、不产生活动/通知/搜索投影，遗留项行只在发布时才建立。写错、重复或放弃的草稿因此是纯粹的个人中间产物。
3. 在只有「编辑」与「发布」两个动作时，误建或废弃的草稿会永久留在草稿箱：既不能回到「不存在」，也不能像正式记录那样作废。
4. 数据库防线在实现前就已存在：`app_runtime` 对 `app.change_records` 只有 `SELECT / INSERT / UPDATE`（`0001_invariants_and_permissions.sql`），没有 `DELETE`。这既是正式记录不可物理删除的最终防线，也意味着「允许删除草稿」必须显式决策，不能靠放开整表权限顺带实现。

## 决策

### 1. 只有 `DRAFT` 可以通过接口物理删除

新增路由 `deleteRecordDraft`（`DELETE /api/v1/projects/{projectId}/record-drafts/{recordId}`）：

- 匿名 / 停用 401；非成员、已移除成员、真实归属不匹配、记录不存在或不是 `DRAFT`、以及删除后的普通读取，一律 404；
- 父级（项目 / 模块 / 功能）不可写 404；
- `If-Match` 必填并映射记录 `row_version`，不一致 409 `RECORD_VERSION_CONFLICT`，与编辑同一语义；
- CSRF + 同源 + 数据库级幂等；删除成功后同一幂等 Key 重放返回同一 200 结果，重放不依赖已删除的草稿行存在；
- 独立草稿与来源草稿共用这条路径：删除不与来源任务、已发布历史或遗留项发生任何级联，来源任务的 `work_status`、完成信息与状态历史都不变。

### 2. 物理删除收进 `SECURITY DEFINER` 函数，不放开表级权限

迁移 `0026_record_draft_delete.sql` 新增 `app.delete_change_record_draft(p_project_id, p_record_id, p_expected_row_version) RETURNS BOOLEAN`：

- `SECURITY DEFINER` + `SET search_path = pg_catalog, app`，`REVOKE ALL FROM PUBLIC` 后只 `GRANT EXECUTE TO app_runtime`；`app_runtime` 对 `app.change_records` 仍没有 `DELETE`，绕过函数的直接删除继续失败；
- 函数内 `SELECT ... FOR UPDATE` 锁目标行；`status <> 'DRAFT'` 抛 `check_violation`（已发布 / 已作废记录由数据库兜底拒绝）；行版本不一致返回 `false`，由服务端映射 409；
- 草稿若意外存在遗留项行，函数抛错而不是静默连带删除——状态机被破坏时不掩盖问题；
- 子行按 `change_record_external_links` → `change_record_feature_impacts` → `change_records` 顺序删除（子表外键为 `ON DELETE restrict`）。

调用方 `RecordDraftsService.remove` 先按既有锁序取得 `project -> module -> feature -> changeRecord` 的共享 / 更新锁，再在同一事务内调用该函数。

### 3. 删除写审计，但不写活动、通知与搜索投影

删除在同一 `UnitOfWork` 内追加不可变审计 `record.draft.delete`（删除前快照 + `after: null`），供管理员追溯「谁删了哪条草稿」。**不**写 `ActivityWritePort`、通知或搜索投影：未发布草稿本来就不出现在项目动态、通知与搜索里，删除也不应产生新的对外事件。

### 4. 前端入口在「编辑草稿」弹窗，删除前二次确认

草稿详情弹窗的「继续编辑」进入编辑弹窗后，页脚左侧新增实底红色「删除草稿」按钮（只对已存在的草稿渲染；实底红直接复用 antd 主题的 `colorError` `#c0453f`，与「作废记录」「解除合并」的 `danger` + `primary` 同一套样式），点击弹确认层（`tone="danger"`，说明「不能恢复」且「已经发布的迭代记录不受影响，只能在记录详情里作废」）。成功后失效草稿列表与全部项目草稿缓存、清掉该草稿详情查询并关闭弹层，同时清掉 URL 里的 `recordId`，避免详情弹层残留已删除的草稿；失败保留草稿与输入并只提示原因。

### 5. 非目标

- 不提供已发布 / 已作废记录的删除，也不引入草稿的「作废」态或回收站；
- 不为 `app_runtime` 放开 `app.change_records` 的 `DELETE`，也不新增墓碑列；
- 不改 [ADR-024](ADR-024.md) 的 `DRAFT -> PUBLISHED -> VOID` 与 `VOID -> PUBLISHED` 状态机；
- 不把草稿删除做成软删除或延迟清理任务。
