# ADR-052：已删除项目的完整动态过程与删除操作唯一入口

- 状态：Accepted
- 基线固化：2026-09-28
- 接受依据：用户 2026-09-28 指示——「有两个重复了，如果是被删除了的项目，就只有最晚的一个可以进行还原和彻底删除的操作，而且不要隐藏之前的创建和操作的动态过程，要有从创建到删除的完整过程，然后刷选的下拉框增加一个选项叫『已删除项目』」。
- 修订关系：**修订 [ADR-050](ADR-050.md) 第 5 节的服务端收窄**——原口径「不在授权范围内但已删除 ⇒ 只下发 `activityType = PROJECT_DELETED` 一行」改为「下发该项目链的全部 `MEMBER` 可见动态」。ADR-050 的其余决策（`listProjectDeletions` 路由、审计链入口、非目标）不变；[ADR-051](ADR-051.md) 的还原与彻底删除动作不变。
- 关联：[ADR-008](ADR-008.md)（审计只追加）、[ADR-049](ADR-049.md)（软删除、退出可见范围）、[ADR-050](ADR-050.md)（删除记录可见性）、[ADR-051](ADR-051.md)（还原与彻底删除）。

## 背景

1. ADR-050 把「删除项目」这条动态公开给全部登录用户，同时为了「不让删除前的历史借例外回放」，在服务端把该例外收窄到 `PROJECT_DELETED` 一行（`ActivityQueryService` 的 `DELETED_PROJECT_ACTIVITY_TYPES`）。
2. 收窄在界面上产生了三个问题，用户在第一轮使用后逐一指出：
   - **重复且都能操作**：项目可以被「删除 → 还原 → 再删除」，同一个 `projectId` 因此留下多条 `PROJECT_DELETED` 动态。台账（`listProjectDeletions`）按项目给出当前删除状态，前端用 `projectId` 匹配，于是**每一条历史删除行**都渲染出「还原项目 / 彻底删除」，看上去像两个独立的可操作对象。
   - **过程被隐藏**：因为只下发删除行，已删除项目在动态流里看不到创建、模块、功能、任务、记录与成员变更，只剩「删除项目」一条孤立记录，与用户要的「从创建到删除的完整过程」不符。
   - **无法聚焦**：项目筛选下拉只有「全部项目 + 活跃项目」，已删除项目没有独立入口，只能混在「全部项目」里靠肉眼找。
3. 三处都只在读取层：写入侧（审计 `project.delete`、动态 `PROJECT_DELETED`、`projects.deleted_at/deleted_by`）与 ADR-051 的动作实现都没有缺口。

## 决策

### 1. 已删除项目下发整个项目链的 `MEMBER` 可见动态

- `ActivityQueryService.resolveAccess` 的返回值由「是否走收窄读」改为读取来源 `"scope" | "deleted-project"`，`"deleted-project"` 不再追加 `activityTypes` 过滤：项目不在授权范围内但 `isDeletedProject(projectId)` 为真时，下发该项目链**全部 `MEMBER` 可见**的投影行。
- `visibilityScopes` 仍是 `["MEMBER"]`：`ADMIN_ONLY` 行不随该例外回放，`includeAdminOnly: true` 对已删除项目无效——管理员看到的与普通成员完全一致。
- 「不存在」「从未有权访问」「已移除成员」的判定不变：仍是 404（`ActivityAuthorizationError`），不泄露资源存在性；未删除项目的跨项目读取行为不变。
- `ActivityProjectionReader.read` 的 `activityTypes` 可选参数失去唯一调用方，连同 SQL 过滤与注释一并删除，避免留下与现行口径矛盾的死代码。

**影响（有意放宽）**：已删除项目的名称、创建过程、成员与任务/记录动态，对**全部登录用户**可见。理由是项目一旦删除就不存在授权范围（[ADR-049](ADR-049.md) / [ADR-050](ADR-050.md)），「删除前的过程」与「删除这件事」同属一条组织级事实；若将来改为「只有参加过该项目的人可见完整过程」，必须新增 ADR 并同步权限矩阵与集成测试。

### 2. 同项目多次删除时，只有最新一条提供还原与彻底删除

- 前端在已加载的动态里按 `projectId` 取时间序第一条 `PROJECT_DELETED`（活动流已按 `occurredAt DESC, id DESC` 合并），只有该行的动作区渲染 `ProjectDeletionActions`；其后的历史删除行只作为过程记录保留，不再挂载「还原项目 / 彻底删除」。
- 判定落在**渲染层**而非数据层：历史删除行仍然是完整的动态行（时间、操作者、摘要、项目名、原始快照），只是没有动作；服务端 `listProjectDeletions` 的台账语义（一个项目一条当前状态）不变。
- 已还原的项目不在台账里，所有删除行都不出现动作——与 ADR-051 的既有行为一致。

### 3. 已删除项目链的所有行都不提供跳转，筛选下拉新增「已删除项目」

- 「查看对象」的抑制条件由「`activityType === "PROJECT_DELETED"`」扩大为「该行的项目在删除台账里」：模块 / 功能 / 任务 / 记录页面对已删除项目不可用，历史行同样不留死链（ADR-050 第 6 节第 6 条的口径按此执行）。
- 项目筛选下拉新增固定选项**「已删除项目」**（值 `"deleted"`）：选中后取数范围收窄为台账里的项目 ID 集合，只请求这些项目的动态；台账为空时给出「暂无已删除项目」空态，且不发出空的动态请求。
- 「全部项目」视图继续包含已删除项目的完整动态（第 1 节的直接结果）；删除台账的读取时机由「仅全部项目」扩展为「全部项目或已删除项目」，锁定单项目视图仍不请求台账。
- 契约、Route Registry、权限矩阵与数据库**零改动**：`activityType` 在契约里是自由字符串，筛选选项是纯前端行为。

### 4. 非目标

1. **不**为已删除项目恢复任何内容入口：不提供「查看对象」，也不按项目 ID 重新开放模块 / 功能 / 任务 / 记录页面（ADR-049 第 9 节、ADR-050 第 6 节不变）。
2. **不**改变台账与还原 / 彻底删除的服务端权限与数据库边界：动作仍只由 ADR-051 的 `restoreProject` / `purgeProject` 提供，前端「唯一入口」只是展示层收敛。
3. **不**把 `ADMIN_ONLY` 行纳入公开范围，也不把审计读取下放给普通成员（ADR-042 的读取留痕只在管理员路径上）。
4. **不**为已删除项目的动态单独建列表页或二级路由：它仍混排在项目动态流的同一时间线里。

## 影响与验证

- **后端**：`apps/api/src/modules/activity/activity-query.service.ts`（`ActivityAccess` 类型 + `resolveAccess` 语义 + 去掉收窄）、`apps/api/src/modules/activity/activity-projection.reader.ts`（删除 `activityTypes` 参数与 SQL 过滤）。
- **前端**：`apps/web/src/features/activity/ActivityWorkspace.tsx`（`DELETED_PROJECTS` 选项与取数范围、`latestDeletionIdByProject`、已删除项目链抑制「查看对象」、台账加载态与「暂无已删除项目」空态）。
- **测试**：
  - `apps/api/test/activity-query.integration.test.ts`：已删除项目对任意登录用户（非成员、仍在册成员、管理员）下发 `MEMBER` 可见的 `PROJECT_DELETED` + `TASK_COMPLETED`，`ADMIN_ONLY` 的 `CHANGE_RECORD_VOIDED` 不出现；`includeAdminOnly: true` 不扩大范围；未删除项目的跨项目读取仍是 `ActivityAuthorizationError`。
  - `apps/api/test/activity-notifications-api.integration.test.ts`（HTTP 层）：同时存在删除行与删除前历史行的已删除项目，任意登录用户取到两行（倒序 `TASK_COMPLETED` → `PROJECT_DELETED`），并通过 `activityPageSchema`；非成员读其他未删除项目仍 404。
  - `apps/web/src/features/activity/ActivityWorkspace.deletions.test.tsx` 新增 3 例：同一项目两条删除记录只有最新一条保留还原与彻底删除；删除前的历史动态一并展示且不给「查看对象」；项目筛选下拉提供「已删除项目」选项。
