# ADR-034：项目归档申请—审核（双人同意）、任务归档与父级归档前置校验

- 状态：Accepted
- 基线固化：2026-09-16
- 修订：本 ADR 中「`LEADER` 或 `PROJECT_ADMIN` 可执行」的角色口径已由 [ADR-039](ADR-039.md) 改为「任意活跃成员可执行」（`PROJECT_ADMIN` 已移除）。申请—审批分离、任务/功能归档前置校验、组长保护等其余决策不变。
- 取代/收紧：收紧 [ADR-033](ADR-033.md) 中「整个项目归档/恢复由系统管理员单方执行」以及「功能归档仍仅系统管理员」的部分；ADR-033 的项目内角色模型、成员管理与模块归档/恢复授权不变。同步收紧开发工作书 F-06 与三份基线设计文档中「项目归档由系统管理员单方执行」的表述。

## 背景

1. 业务要求项目归档不是单个管理员的一键动作，而是「申请—审核」的双人同意流程：项目组长（LEADER）或项目管理员（PROJECT_ADMIN）发起归档申请，只有总管理员（系统管理员，`is_admin`）能批准并真正归档；驳回只结束申请、不改变项目状态。
2. 归档前置校验只针对任务，且以「已收尾」为准：项目与模块归档都要求作用域内不存在 `lifecycle_status = 'ACTIVE'` 且 `work_status = 'TODO'` 的任务（已完成 DONE、已取消 CANCELED 与已归档都算收尾）；功能（FEATURE）不参与该口径，不存在「功能必须先归档」的拦截。
3. 任务此前只有取消（CANCELED）语义，缺少「从活跃视图移除但保留历史」的归档语义；用户要求模块与任务弹窗底部提供归档入口，且普通组员没有该权限。

## 决策

### 1. 项目归档 = 申请 + 审核（双人同意）

- 新增 `requestProjectArchive`（`POST /api/v1/projects/{projectId}/archive-requests`）：系统管理员、本项目 LEADER、本项目 PROJECT_ADMIN 可发起；普通成员 403 `PROJECT_ARCHIVE_REQUEST_FORBIDDEN`，非成员或其他项目 404。请求体 `reason` 必填（1..2000），要求 CSRF 与 `Idempotency-Key`，不要求 `If-Match`（申请不修改项目行）。申请只落一行 `app.project_archive_requests`（`status = PENDING`），项目状态与 `row_version` 不变。
- 新增 `approveProjectArchive`（`POST /api/v1/projects/{projectId}/archive-requests/{requestId}/approve`）：只有系统管理员（`adminSession` 且 `is_admin`）可批准。`If-Match` 必须匹配项目当前 `row_version`；批准在同一事务内把申请置为 `APPROVED`、把项目置为 `ARCHIVED` 并递增 `row_version`。
- 新增 `rejectProjectArchive`（`POST /api/v1/projects/{projectId}/archive-requests/{requestId}/reject`）：同样只有系统管理员可执行；只把申请置为 `REJECTED`（批注可选、不超过 2000 字），项目状态不变。
- 同一项目同一时刻只允许一条 `PENDING` 申请（部分唯一索引 `project_archive_requests_one_pending`），重复申请 409。系统管理员直接调用既有 `archiveProject` 时，同一事务内把待审申请置为 `CANCELED` 并在审计 payload 记录 `cancelledArchiveRequestIds`，避免「项目已归档但申请仍待审」。
- 申请、批准与驳回都在同一个 `UnitOfWork` 内写不可变审计（`project.archive.request` / `project.archive.approve` / `project.archive.reject`）、活动（`PROJECT_ARCHIVE_REQUESTED` / `PROJECT_ARCHIVED` / `PROJECT_ARCHIVE_REJECTED`）、搜索投影与通知（申请通知全部系统管理员，批准与驳回通知申请人）。
- **申请权与审批权分离是硬约束**：LEADER 与 PROJECT_ADMIN 只能申请、不能批准；系统管理员也可以申请并自审，这是双人同意在「不存在更高审批人」时的唯一豁免。

### 2. 父级归档前置校验（只针对任务）

- 项目归档申请与项目归档批准：要求项目下不存在 `lifecycle_status = 'ACTIVE'` 且 `work_status = 'TODO'` 的任务，否则 409 `PROJECT_ARCHIVE_TASKS_OPEN`。
- 模块归档：要求该模块下不存在 `lifecycle_status = 'ACTIVE'` 且 `work_status = 'TODO'` 的任务，否则 409 `MODULE_ARCHIVE_TASKS_OPEN`。
- 功能（FEATURE）不参与该口径：归档功能仍只要求父模块 ACTIVE，不检查任务，也不要求任何下级归档。
- 校验在服务端、同一事务内、按「项目 → 模块」父到子持锁后执行，不信任客户端提交的状态。

### 3. 任务归档与恢复

- 新增 `archiveTask` / `restoreTask`（FEATURE scope）与 `archiveModuleTask` / `restoreModuleTask`（MODULE scope），只切换 `tasks.lifecycle_status`（`ACTIVE` 与 `ARCHIVED` 互转）。
- 权限：系统管理员、本项目 LEADER、本项目 PROJECT_ADMIN；普通成员 403 `TASK_ARCHIVE_FORBIDDEN`，非成员或跨项目 404。用户口径中的「项目创造者」由 ADR-033 的组长身份承载。
- 原因必填、`If-Match` 乐观锁、CSRF 与 `Idempotency-Key` 必填；项目、模块与功能父级必须 ACTIVE，状态不符 409。
- 父级口径：命令只要求项目 ACTIVE；模块或功能已归档时**仍允许归档其任务**（收尾动作）。否则「先归档功能 → 其任务无法归档 → 模块下永远存在 ACTIVE 任务 → 模块无法归档」会形成死锁。恢复仍要求模块与功能父级链全部 ACTIVE，避免已归档父级下重新出现活跃任务；HTTP 幂等解析阶段与 `execute` 使用同一口径。
- 前端入口：任务编辑弹窗底部左侧提供「归档」/「恢复」按钮（`data-testid=task-modal-lifecycle`，与模块、功能弹窗一致），普通成员不可见；确认弹窗要求填写操作原因，携带 `If-Match` 与 `Idempotency-Key`，成功后刷新任务、模块与活动视图。父级已归档、任务自身只读时，有归档角色的用户仍可打开该弹窗（表单只读并给出提示），否则真实场景里「功能已先归档」会使归档入口不可达。
- 模块归档 409 `MODULE_ARCHIVE_TASKS_OPEN` 与项目归档 409 `PROJECT_ARCHIVE_TASKS_OPEN` 的文案都带未收尾任务数量，并指引到任务弹窗底部完成或归档；任务「完成」即算收尾，归档只是可选的收尾动作，不再是上级归档的硬前置。
- 工作状态（`work_status`）、完成快照与 `task_status_history` 不可变：归档与恢复不写状态历史，也不改变既有完成统计口径。
- 同事务写审计 `task.archive` / `task.unarchive`、活动 `TASK_ARCHIVED` / `TASK_RESTORED` 与搜索投影。
- 「删除任务」在界面上按逻辑归档实现，不提供物理删除；ADR-033 的 `task.deleted` 双人同意规则保持不变，也不是本 ADR 的路径。

### 4. 功能归档/恢复权限与任务、模块对齐

- 功能归档（界口语「删除功能」）与恢复自 ADR-034 起与任务、模块归档同一口径：系统管理员、本项目 LEADER 或 PROJECT_ADMIN 可执行，普通成员 403 `FEATURE_MANAGE_FORBIDDEN`，非成员或跨项目 404；路由 `archiveFeature`/`restoreFeature` 的 `authPolicy` 由 `adminSession` 调整为 `session`，角色条件登记在权限矩阵 `conditional` 条目并由服务层在同一事务内校验。
- 功能不参与任务归档前置校验：归档功能只要求项目与父模块 ACTIVE、功能自身 ACTIVE（恢复要求 ARCHIVED），不要求功能下任务已归档，也不要求下级内容先归档。
- 幂等重放门禁同步加入项目角色复核（`replayAuthorizationPolicy`），旧 Key 在新契约下 409；`FeatureItem` 的重放安全字段不变，高风险管理路由的幂等契约版本由 1.2.0 升为 1.3.0。
- 前端入口与模块弹窗一致：归档入口只保留在「编辑功能」弹窗底部（`.calm-action-footer` 左侧，按钮文案「归档」/「恢复」），功能卡片与功能详情页头不再提供归档按钮，仅对已归档功能保留「恢复功能」入口（否则恢复无入口可走）。

### 5. 列表展示

- 项目列表项增加 `currentUserRole` 与 `pendingArchiveRequest`（申请人、申请时间、原因摘要）。前端据此显示「申请归档」「归档申请审核中」以及系统管理员的「批准归档」「驳回申请」。

## 影响与验证

- 迁移：`0016_project_archive_requests.sql`（表、枚举 CHECK、部分唯一索引、origin guard 触发器，`app_runtime` 授予 SELECT/INSERT/UPDATE）。
- 契约：新增 3 条项目归档申请路由与 4 条任务归档/恢复路由；`projectListItemSchema` 增加 `currentUserRole` 与 `pendingArchiveRequest`，`projectListResponseSchema` 改用 `projectListItemSchema`；新增 `TaskArchiveRequest` Schema Registry 条目；`archiveModule` 增加 409 `MODULE_ARCHIVE_TASKS_OPEN` 语义；相关路由的幂等契约版本与重放策略同步升级。
- 权限矩阵：`docs/permissions.md` 新增项目归档申请、批准、驳回与任务归档、恢复条目；`archiveModule` 行补充 409 说明；项目归档申请行口径改为「项目下任务均已收尾」（任务「完成」即算收尾）。
- 测试：`apps/api/test/project-archive-request-api.integration.test.ts`（普通成员 403、非成员 404、存在未收尾任务 409、提交与幂等重放、审计/活动/通知/列表字段、仅系统管理员可审核、批准按 `If-Match` 归档、版本冲突 409、重复批准 409）；`tasks-api.integration.test.ts`（任务归档与恢复不改状态历史、审计与投影、角色 403、跨项目 404、版本与状态 409）；`modules-api.integration.test.ts`（模块下存在未收尾任务时 409；已完成但未归档的任务不再阻塞）；`project-management-api.integration.test.ts`（直接归档项目时待审申请被 CANCELED）。

## 未决与边界

- `lifecycle_status = INVALID` 的任务按「已归档」处理（校验只统计 `ACTIVE`），用户未提出其他要求。
- 审核路由先校验全局管理员身份，因此非管理员（即使不是项目成员）发起审核返回 403 `ADMIN_REQUIRED` 而不是 404；这是有意选择，避免向无权主体暴露「本项目是否有人申请归档」。
- 重复批准一条已归档项目的申请返回 409 `PROJECT_STATE_CONFLICT`（先校验项目状态），而不是 `PROJECT_ARCHIVE_REQUEST_DECIDED`。
