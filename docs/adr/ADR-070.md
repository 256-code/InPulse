# ADR-070：整项目文档导入的初始成员名单必须含创建者与全部任务负责人

- 状态：Accepted（2026-10-14 接受，实现随本批落库）
- 日期：2026-10-14
- 决策人：项目负责人（用户指示）与开发代理共同确认
- 关联：修订 [ADR-064](ADR-064.md) 模式 B（整项目导入）的成员语义——原先「负责人与初始成员解析后自动加入成员（去重、排除创建者）」，现要求文档显式写出全部应加入的人；补充 [ADR-069](ADR-069.md)（工作台的本地确定性预检增加成员名单三项）；沿用 [ADR-065](ADR-065.md)（模板说明行）、[ADR-033](ADR-033.md)（创建者自动成为活跃成员并担任组长）、[ADR-067](ADR-067.md) / [ADR-068](ADR-068.md)（AI 辅助与提示词口径）、[ADR-029](ADR-029.md)（统一错误体）。**无新增路由（仍 110 条）、无数据库迁移（仍 39 个）、无新增依赖、无权限变化**；契约模板常量文本有改动（生成物按 `pnpm contract:generate` 更新，`contract:drift` 无漂移），模板版本仍为 1。

## 1. 背景

用户本轮原话（要点）：

> 我需要增加一个检验，初始成员必须包含创建者以及所有出现在任务负责人中的人
>
> 初始成员必须名字能和目前系统中有的账号相对应

ADR-064 落地后，模式 B（整项目导入）的成员来源是「文档里 `- 初始成员：` 写谁就加谁 + 所有任务负责人一律自动并入」，去重并排除创建者（创建者由创建流程按 ADR-033 自动加入并担任 LEADER）。这条「自动并入」有两个副作用：

1. **名单不完整也不报错**：`- 初始成员：` 整行不写（空名单）时导入照样成功，文档读者（项目成员、后续接手人）看不出这个项目到底该有谁——成员关系只在预览摘要的 `memberAddCount` 里一闪而过。
2. **文档里的成员与项目成员会不一致**：负责人没写进 `- 初始成员：` 会被静默补上，用户看到的草稿与最终成员不是同一份事实；而名字写错对不上账号时却在 422 里报 `MEMBER_UNRESOLVED`，两件事的口径不一致。

用户第二句要求的「名字能和系统里有的账号相对应」，ADR-064 已经做到（按登录名或姓名解析，未找到 422 `MEMBER_UNRESOLVED`、同名多人 422 `MEMBER_AMBIGUOUS`）。本 ADR 要做的是把**名单完整性**也变成同一条 422 裁决，并让工作台在点「预览」之前就看得见缺口。

## 2. 决策

### 2.1 服务端三条行级 ERROR（模式 B，预览即裁决）

`apps/api/src/workflows/document-import.workflow.ts` 的 `preparePlan` 在 `NEW_PROJECT` 分支新增（只在有项目段时判）：

- `MEMBER_REQUIRED`（落在项目行）：`- 初始成员：` 一个令牌都没有 → 422，「整项目导入必须用「- 初始成员：」列出成员，且至少包含创建者本人与全部任务负责人」。
- `MEMBER_CREATOR_MISSING`（落在项目行）：名单里没有创建者本人 → 422，「「- 初始成员：」必须包含创建者本人；请把创建者的姓名或登录名一并写进去」。
- `ASSIGNEE_NOT_INITIAL_MEMBER`（落在该任务行）：某个任务负责人的账号不在名单里 → 422；同一人只在**第一条**命中的任务上报一次（按 userId 去重）。

口径细节：

- 判的是**解析后的账号**，不是字面：名单写登录名 `zhangsan`、负责人写姓名「张三」，只要指向同一账号就算包含，不报。
- `MEMBER_CREATOR_MISSING` 与 `ASSIGNEE_NOT_INITIAL_MEMBER` 只在名单非空时判；空名单已由 `MEMBER_REQUIRED` 一次说清，不再叠报。
- 既有 `MEMBER_UNRESOLVED`（对不上账号）/ `MEMBER_AMBIGUOUS`（同名多人）/ `MEMBER_LIMIT_EXCEEDED`（人数超上限）与「负责人自动并入成员集合」全部保留：三条新 ERROR 会拦住导入，自动并入退化为兜底，不改变去重口径与 `memberIds` 的构成。
- 模式 A（项目内导入）不变：文档不写成员段，负责人必须是目标项目当前活跃成员（`ASSIGNEE_NOT_MEMBER`），导入不隐式改成员关系。

### 2.2 AI 提示词带上「本次导入人」

只靠模板说明行，模型没有理由知道创建者本人是谁，整项目草稿多半会漏掉导入人，用户在预览时被打回。因此：

- `buildSystemPrompt(mode, creatorName?)` / `buildAiAssistMessages({ mode, text, creatorName })` 新增可选 `creatorName`；整项目模式的成员规则由「文档中出现的成员可写入「- 初始成员：」」改成「「- 初始成员：」必填，不能省略。文档里明确写的项目成员 / 参与人 / 团队 / 项目组、补充说明里点名要加入的人、以及所有任务的「负责人」都要写进去（逗号分隔，照抄原文写法，写姓名或登录名都可以）」，并在知道姓名时补一句「必须包含创建者本人（本次导入人，姓名：X）以及全部任务负责人」。
- 姓名由 `document-import-http.service.ts` 的 `assist()` 取：改为 `this.uow.run(...)` + `resolveActorInTransaction(...)` 拿 actor，再经新注入的 `UserReadPort` 读姓名；**姓名只进提示词，不进日志**（`logCall` 的入参仍是 `AiAssistDraftRequest`，不打印 `creatorName`）。
- 取不到姓名时不编造，规则退化为「必须包含创建者本人，以及全部任务负责人」。

### 2.3 工作台本地预检（ADR-069 扩展）与服务端同口径

- `apps/web/src/features/document-import/document-assignee-match.ts` 新增 `checkDocumentMemberCoverage(view, mode, context)`，返回 `memberRequired` / `creatorMissing` / `missingAssignees`；`DocumentImportModal.tsx` 的 `computeMissingItems` 据此新增三条 ERROR 项：`缺初始成员`、`初始成员缺创建者`、`初始成员缺任务负责人`（后者带「缺在哪几条」）。
- **本地只报确定的事**：只认「姓名精确且唯一」「与创建者姓名或登录名一致」两类命中；名单里出现本地读不懂的令牌（多半是登录名）或同名多人时，整体不报负责人缺口——宁可等预览时服务端定案，也不把「其实写了、只是本地读不懂」的人报成漏写。用户目录还没回来、未登录或模式 A 时不做成员判断。
- 左栏必填标记与「必填要素」文案同步：「＋初始成员」按必填变黄；文案改为「参加人员（填写姓名，且必须包含创建者本人与全部任务负责人）」；右栏未匹配区补一句「名字对不上账号时预览会被拒绝」。

### 2.4 模板说明行与生成物

`packages/api-contract/src/contracts/document-import.zod.ts` 的 `DOCUMENT_IMPORT_TEMPLATE` 顶部说明行改两处：`- 初始成员` 一行写成「整项目导入时必填，逗号分隔，写登录名或姓名；须包含创建者本人与全部任务负责人」，第 5 条写成「负责人与初始成员必须是系统里已有的用户（写登录名或姓名）；整项目导入时初始成员必填，且必须包含创建者本人与全部任务负责人，他们会一起加入项目成员」。生成物随 `pnpm contract:generate` 更新；模板版本仍为 1（不改变任何已导入文档的解析结果，只让新文档不再漏写）。

### 2.5 边界不变声明

- 不新增路由（仍 110 条）、不改 Route Registry / Schema / OpenAPI（只有模板常量文本变化）、无数据库迁移（仍 39 个）、无新增依赖、无权限变化。
- 事务边界、Secrets、CSP、统一错误体与幂等口径全部沿用既有 ADR；AI 草稿仍永不直接入库，仍走「预览（只读）→ 确认导入（单事务）」。
- 创建者仍按 ADR-033 由创建流程自动成为活跃成员并担任 LEADER；本 ADR 只要求文档里必须把 TA 写出来，不改变创建流程的成员语义。

## 3. 非目标

- 模式 A（项目内导入）的成员校验：那边要求负责人已是活跃成员、导入不隐式改成员关系，本轮不动。
- 自动补全名单（例如「没写就把负责人填进成员段再导入」）：被明确否掉——要的是导入前说清楚，不是静默补齐。
- 名单的角色 / 组长指定（文档里仍只能写人，不能写角色）、成员顺序与去重语义变化。
- 新增错误码的前端专属能力：仍走既有 `DOCUMENT_IMPORT_INVALID` + 行级 issue 清单展示。
