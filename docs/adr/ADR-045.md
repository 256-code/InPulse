# ADR-045：功能层面下线归档，功能只有 ACTIVE

- 状态：Accepted
- 基线固化：2026-09-24
- 接受依据：用户 2026-09-24 明确要求「要继续」，承接其在功能卡上对琥珀色「已归档」徽章的追问「为什么还有归档相关显示？」——即按 [ADR-044](ADR-044.md) 的同一口径，把功能层归档一并下线。
- 替代：替代 [ADR-034](ADR-034.md) 中**功能归档与恢复**的全部决策（`archiveFeature` / `restoreFeature`、`FEATURE_MANAGE_FORBIDDEN`、`FEATURE_STATE_CONFLICT`、功能编辑弹层底部的归档 / 恢复入口）；ADR-034 中的任务归档与父级归档前置校验继续有效（任务层 `parent-not-active` 保留）。
- 修订：修订 [ADR-044](ADR-044.md) 中「功能列表保留『进行中 / 未开始 / 已归档』三档」的表述——功能列表与模块列表改为同一口径，只有「进行中 / 未开始」两档。
- 修订：修订 [ADR-039](ADR-039.md) 中把 `archiveFeature` / `restoreFeature` 列入「项目内管理操作」的清单，两条路由随之下线。

## 背景

1. 与模块同理（[ADR-044](ADR-044.md)）：把一个功能标成「已归档」只换来一个只读态。功能虽然是会被收尾的对象，但归档并没有形成真实使用场景——团队既不会因此少看一个功能，也不会因此收回任何权限；真正要停掉一个功能，实际做法是把它下面的任务收尾，而不是把功能本身标成只读。
2. 归档同时带来一整套连带复杂度：任务、聚合组、迭代记录、遗留项、外部链接、记录发布与聚合读都要跟着维护「所属功能已归档」分支（`TASK_PARENT_ARCHIVED`、`TASK_IMPACT_ARCHIVED`、`TASK_MERGE_PARENT_ARCHIVED`、`LEFTOVER_PARENT_ARCHIVED` 与「排除归档影响功能」），功能自身还要额外定义「非空原因 + 最多 2000 字」的归档门禁。
3. 项目（[ADR-043](ADR-043.md)）与模块（[ADR-044](ADR-044.md)）都已下线归档后，功能是最后一层「父级已归档 → 下级只读」的语义来源；保留它会继续把整条父级链的复杂度锁在代码里。
4. 任务、迭代记录与遗留项的归档仍然有真实语义（「从活跃视图移除但保留历史」），本次不动。

## 决策

### 1. 功能状态只有 `ACTIVE`

数据库 `features_status_check` 收紧为 `CHECK (status = 'ACTIVE')`；`archived_at` 列保留为只读历史列但恒为空，由 `features_archived_at_null_check CHECK (archived_at IS NULL)` 兜底（迁移不可逆，不做物理删列）。迁移 `0025_feature_archive_removal.sql` 负责升级窗口：先摘除 `features_archive_state_check`，再在临时关闭 `features_row_version` 触发器的情况下把存量 `ARCHIVED` 行回填为 `ACTIVE` 并清空 `archived_at`（不递增 `row_version`），`SET CONSTRAINTS ALL IMMEDIATE` 结算延迟约束事件后立即恢复触发器，最后收紧状态 CHECK 并新增兜底约束；`status` 成为常量列后，`features_module_status_idx` 重建为去掉 status 的 `features_module_id_idx (project_id, module_id, id)`。历史迁移不改写。

### 2. 两条归档路由与原因 Schema 整体下线

- 路由：`archiveFeature`、`restoreFeature` 从 Schema Registry、Route Registry、权限矩阵、OpenAPI 与生成客户端移除（Route Registry 100 → 98 条）；
- Schema：`FeatureArchiveRequest`（原因）整体删除，功能不再有「非空原因 + 最多 2000 字」的归档语义；
- DTO：`featureItemSchema` 去掉 `status` 与 `archivedAt`，`featureStatsSchema` 新增 `completedTaskCount`（功能档位改由它派生），`createFeature` / `updateFeature` 的幂等契约版本统一升到 **1.4.0**（响应 Schema 变化会让旧 Key 在新契约下 409）。

### 3. 功能写前检查收窄为「存在 + 归属」

`FeatureWriteCheckResult` 由 `allowed | not-found | parent-not-active` 收窄为 `allowed | not-found`，`FeatureForWriteResource` 去掉 `status`；`ProjectWriteAccessFailure` 去掉 `feature-not-active`；`FeatureReadPort.count` 去掉 `status` 过滤参数。功能自身的编辑只保留版本冲突 `FEATURE_VERSION_CONFLICT`，`FEATURE_STATE_CONFLICT` 随单态消失。功能下级的父级 `FOR SHARE` 取锁仍由 `FeatureQueryPort` 承担，锁顺序不变。

### 4. 功能下级的「父级已归档」分支整体删除

任务、聚合组、迭代记录、遗留项、外部链接、记录发布与聚合读中所有「所属功能已归档」的写前检查与错误码（`TASK_PARENT_ARCHIVED`、`TASK_IMPACT_ARCHIVED`、`TASK_MERGE_PARENT_ARCHIVED`、`LEFTOVER_PARENT_ARCHIVED` 与「排除归档影响功能」）一并删除；功能创建 / 编辑 / 详情 / 列表 / 相似候选不再按状态过滤。任务仍要求所属项目、模块与功能存在且归属正确。

### 5. 功能展示口径：只剩「进行中 / 未开始」两档

功能卡上的档位标签原本有「已归档」第三档，本次只保留由 `stats.completedTaskCount` 派生的「进行中 / 未开始」两档（与模块同一口径），列表分组与组内 `id` 升序顺序不变。前端在 `resource-lifecycle.ts` 新增 `FeatureLifecycleKind` / `featureLifecycleKind` / `featureLifecycleLabel` / `featureLifecycleTone`，不再读取服务端 `status`。

### 6. 前端只剩「编辑功能」

功能卡与功能详情页头不再有归档 / 恢复入口，编辑弹层底部只剩「取消 / 保存」，页头不再有「功能已归档」只读提示与禁用态；归档确认流程依赖的 `Values.reason`、`canArchiveResources` 与 `card-archived` 样式一并删除。

### 7. 非目标

1. 不删除任务、迭代记录与遗留项的归档 / 恢复，也不改动它们的父级归档前置校验（项目与模块自 ADR-043 / ADR-044 起已无归档态，本次只剩「存在 + 归属」）。
2. 不新增功能删除（物理删除）、功能级状态或功能生命周期档位。
3. 不改动 `archiveTask` / `restoreTask` 与 `archiveModuleTask` / `restoreModuleTask`：它们是任务归档命令，与功能归档无关，继续有效。
4. 不清理历史审计、历史动态与历史通知中既有的功能归档记录，只保留只读展示。
5. 不修改已合并的历史迁移，也不物理删除 `features.archived_at` 列。
