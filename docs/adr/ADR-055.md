# ADR-055：项目保留期到期自动彻底删除

- 状态：Accepted
- **已被取代（2026-10-09，[ADR-062](ADR-062.md)）**：删除已是物理的，不再存在「30 天后彻底删除」的第二阶段。`ProjectAutoPurgeService` / `ProjectAutoPurgeScheduler`、`PROJECT_AUTO_PURGE_ENABLED` / `PROJECT_AUTO_PURGE_RETENTION_DAYS` / `PROJECT_AUTO_PURGE_BATCH_SIZE` 与 SYSTEM 链的 `project.purge`（`trigger = AUTO_RETENTION`）整体删除，保留期概念不再存在。本文件仅作变更历史。
- 基线固化：2026-09-30
- 修订关系：**扩展 [ADR-051](ADR-051.md)**（新增「到期自动触发」这一条触发路径，手工 `purgeProject` 路由、权限与审计口径全部不变）。ADR-049 的软删除语义、ADR-050 / [ADR-052](ADR-052.md) 的删除记录可见性与呈现方式、[ADR-053](ADR-053.md) 的组长不变量均不受影响。
- 关联：[ADR-008](ADR-008.md)（SYSTEM 审计链只能追加）、[ADR-018](ADR-018.md)（数据库角色分离）、[ADR-020](ADR-020.md)（备份保留窗口）、[ADR-031](ADR-031.md)（管理员高风险门禁）、[ADR-035](ADR-035.md)（不发送悬挂深链通知）。

## 背景

1. ADR-051 交付的「彻底删除」是**手工动作**：系统管理员（或本项目组长还原之后）在项目动态的删除记录行上点「彻底删除」，项目与其 `PROJECT:<id>` 审计链才会被物理删除。软删除的项目会一直留在库里，不点就永远不消失。
2. 用户希望删除有**保留期**：软删除满 30 天自动彻底删除，把「删除台账」控制在一个有界的规模内，而不是等人工清理。
3. 第二条要求定义了计时口径：**还原过就按最后一次删除计算**。这条要求不需要额外状态——还原会把 `deleted_at` / `deleted_by` 清空，再次删除会写入新的删除时间，因此「保留期从 `deleted_at` 起算」天然就是「从最后一次删除起算」。
4. 手工彻底删除已经具备全部数据面能力：`app.purge_project(INTEGER)` 窄口（`SECURITY DEFINER`、fail closed、被删项目自己的审计链随项目删除、SYSTEM 链留一条 `project.purge`）。因此本次要解决的是**谁来触发**与**什么时候触发**，而不是再造一条删除路径。

## 决策

### 1. 保留期 30 天，计时只认「最后一次删除」

- 保留期以 `app.projects.deleted_at` 起算，条件写成数据库侧的时间比较：`deleted_at <= now() - make_interval(days => $1::integer)`。用数据库时钟而不是应用进程时钟，避免多实例或容器时钟偏差导致同一个项目被判定为「到期」与「未到期」两种结论。
- 还原（`restoreProject`）清空 `deleted_at`，重新删除（`softDeleteProject`）写入新的 `deleted_at`，因此「还原 → 再删除」自动把 30 天重新计时，不需要任何额外列或计数器。这也是本 ADR 不做「首删时间」「累计删除次数」等字段的原因。
- 保留期默认 30 天，可由 `PROJECT_AUTO_PURGE_RETENTION_DAYS` 覆盖（正整数，非法值 fail closed，进程启动即失败）。

### 2. 触发路径：服务端进程内调度，不引入外部定时设施

- 新增 `ProjectAutoPurgeService` 与 `ProjectAutoPurgeScheduler`，随 `ProjectManagementModule` 启动；形态与既有 `SessionCleanupScheduler` 一致，不引入 cron 容器、Kubernetes CronJob、队列或外部调度系统（这些都在仓库非目标内）。
- 调度节奏：启动后 **1 分钟**首跑，成功后**每小时**一次，本轮抛错时 **60 秒**后重试。定时器 `unref()`，不会阻塞进程退出。
- 关闭开关：`NODE_ENV=test` 时不启动（避免 vitest 进程被后台定时器挂住）；`PROJECT_AUTO_PURGE_ENABLED=false` 可整体关闭生产调度。
- 单次运行最多处理 `PROJECT_AUTO_PURGE_BATCH_SIZE` 个项目（默认 20），其余候选等下一轮继续，避免一次运行长时间占用连接。
- 环境变量都有默认值，因此**不改** `deploy/compose.yaml`、不新增 Secret、不改发布清单（与 `SESSION_CLEANUP_*` 的处理方式一致）。

### 3. 执行语义：候选只读筛选，逐项目独立事务加锁复核后删除

- 第一段只读查询（`listAutoPurgeCandidates`）按 `deleted_at ASC, id ASC` 取到期候选的 `id` 与 `deleted_at`，不写库、不加长事务。
- 每个候选在**自己的事务**里：`SELECT ... FOR UPDATE OF p` 加行锁并按保留期复核（`findExpiredDeletedProjectForChange`）→ 命中才调用 `app.purge_project` → 在 **SYSTEM** 审计链追加 `project.purge`。
- 复核未命中即**跳过**（`skippedProjectIds`）：项目已被还原、已被并发彻底删除，或还原后重新删除导致删除时间被刷新为新值——这三种情况都不允许删。
- 单个项目失败只回滚该项目的事务并记录日志（`failedProjectIds`），下一轮重试；一项目失败不阻塞同批其它项目，也不需要人工介入。
- 逐项目独立事务保证「一个项目的失败或超时不拖累整批」，且事务内无网络请求、无长任务（与 ADR-051 相同约束）。

### 4. 审计：记在 SYSTEM 链，并标明是自动触发

- 自动路径与手工路径写同一个动作名 `project.purge`，但正文不同：`actorType: "SYSTEM"`、`actorId: null`、`actorRole: "SYSTEM"`、`trigger: "AUTO_RETENTION"`、`retentionDays`、`deletedAt` 与 `deletedBy` 快照（记录「谁在何时删的」）以及 `records`（七项计数）。手工路径（ADR-051）保持 `actorRole: "SYSTEM_ADMIN"`、无 `trigger` 字段，二者可由审计正文区分。
- 审计链选择与 ADR-051 相同：项目自己的 `PROJECT:<id>` 链随项目一起删除，因此这条记录只能写在 SYSTEM 链上（`projectId: null`）。这是 ADR-008 的唯一例外，例外范围仍被 `app.purge_project` 写死。
- 自动路径没有客户端请求，因此不涉及 CSRF、幂等键与路由契约；权限门禁是「服务端后台任务以 SYSTEM 身份执行 ADR-051 已批准的窄口」。

### 5. 多实例与并发安全

- 候选列表只是提示，最终判定在行锁内：两个实例同时看到同一候选，只有一个能拿到锁并通过复核，另一个复核时项目已不存在 → 跳过。
- `app.purge_project` 自身 fail closed（要求 `deleted_at IS NOT NULL`），因此「已被手工彻底删除」「刚被还原」的项目在数据库层也会被拒绝，不会出现第二份删除或半删状态。

### 6. 非目标

1. **不**新增路由、契约、权限矩阵条目与生成客户端产物：自动删除没有客户端入口，手工入口仍是 `purgeProject`（ADR-051）。
2. **不**为自动删除发站内通知（ADR-035：删除后项目深链必成死链，通知只能标记已读不能作废）；也**不**在界面上加「剩余保留天数 / 到期倒计时」。
3. **不**追溯修改历史删除记录的可见性：删除行与其原始快照在项目被彻底删除时随项目活动投影一起消失（ADR-051 第 7 节第 5 条不变）。
4. **不**回收或保留项目编码（ADR-051 第 4 节结论不变）。
5. **不**做「删除前人工提醒 / 二次确认 / 审批」，也**不**提供被自动删除后的恢复路径——保留期就是唯一的缓冲。
6. **不**把保留期做成按项目可配置的字段（不做每项目一个保留期）。

## 影响与验证

- **数据库**：无迁移、无新表、无新列、无权限变更。复用迁移 `0031_project_purge.sql` 的 `app.purge_project`、`app.protect_unclassified_module` 放行分支与既有角色授权。
- **契约**：无改动。Route Registry 仍为 99 条，OpenAPI 与生成客户端无漂移。
- **后端**：`projects/projects-write.port.ts`（新增 `ExpiredProjectRecord` 与 `listAutoPurgeCandidates` / `findExpiredDeletedProjectForChange`）、`postgres-projects-write-port.ts`（候选查询 + 与手工路径共享的 `readDeletedProjectForChange`，后者把「是否要求到期」做成可选参数，手工路径行为不变）、`project-auto-purge.service.ts`（候选筛选、逐项目事务、复核、删除、SYSTEM 审计与失败隔离）、`project-auto-purge.scheduler.ts`（首跑 1 分钟 / 每小时 / 失败 60 秒重试、`unref()`、测试环境与开关关闭）、`project-management.module.ts`（注册两个 provider）。
- **配置**：`PROJECT_AUTO_PURGE_RETENTION_DAYS`（默认 30）、`PROJECT_AUTO_PURGE_BATCH_SIZE`（默认 20）、`PROJECT_AUTO_PURGE_ENABLED`（`"false"` 关闭）；非法正整数配置 fail closed。
- **测试**：
  - `apps/api/test/project-auto-purge.service.test.ts` 5 例（单测，假端口）：无候选时只读一次且不写审计；锁内复核未命中时跳过且不删除；成功路径的审计形状（SYSTEM 身份、`targetId`、`trigger = AUTO_RETENTION`、`records` 计数）；单项目失败隔离（失败项目进 `failedProjectIds`，同批其它项目照常删除）；环境变量默认值与非法值 fail closed。
  - `apps/api/test/project-auto-purge.integration.test.ts` 4 例（真实 PostgreSQL）：到期项目被物理删除（项目行、模块、成员归零，`PROJECT` 审计链消失，SYSTEM 链恰好一条 `project.purge` 且 `trigger = AUTO_RETENTION`、`records.modules` / `records.members` 计数正确）；删除 29 天的项目**不**被删除且不写审计；「删除 40 天前 → 还原 → 立刻重新删除」不删、「还原 → 再删除满 31 天」删除（锁定「按最后一次删除计时」）；未删除项目不进候选，且 `findExpiredDeletedProjectForChange` 对活跃 / 刚删除 / 已到期三类目标分别返回 undefined / undefined / 记录。
- **未覆盖 / 已知偏差**：保留期边界是「满 30 天即删」，调度粒度为小时级，因此实际删除时间会落在到期后的 0～1 小时内（首个候选还受批大小影响）。真实主机上的长跑验证、`pnpm test:e2e` 与 GitHub Actions 未在本批执行。

## 后果

- 软删除不再是「永久留在库里」，删除台账规模由保留期自动收敛；用户要保住一个项目必须在 30 天内还原。
- 自动删除与手工删除共用同一条窄口、同一套复核与同一条 SYSTEM 审计链，因此权限面、数据边界与可追溯性都没有被放宽。
- 代价是「删除满 30 天后不可恢复且无提醒」：这是用户明确选择的取舍，本 ADR 把它写成不变量——如需提醒或更长的保留期，必须新增 ADR 并同步权限矩阵、测试矩阵与本节。
