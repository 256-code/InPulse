# ADR-049：项目删除（软删除）与删除权限

- 状态：Accepted
- 基线固化：2026-09-28
- 接受依据：用户 2026-09-28 指示——「在编辑项目里面增加一个删除项目的功能，只有组长和系统管理员有删除的权限」。
- 修订关系：在 [ADR-039](ADR-039.md) 的「项目内管理权限下放给全体活跃成员」之上**新增一个例外**：删除项目不放给普通成员，只有系统管理员与本项目组长可以执行（与 [ADR-048](ADR-048.md) 的组长身份口径同源）。ADR-039 的其余下放口径不变。
- 关联：软删除与「业务历史默认通过归档、作废或新版本保留」一致（`AGENTS.md` 第 6 节）；[ADR-043](ADR-043.md) 已下线项目归档，本 ADR 不恢复归档，只提供「退出可见范围」的删除语义。

## 背景

1. 项目此前没有任何删除入口：`projects` 只有创建、编辑与状态切换。
2. 物理删除在本仓库不可行，实测 `app.projects` 被 12 张表以 `RESTRICT` 外键引用（`activity_projection`、`audit_chain_heads`、`audit_logs`、`code_sequences`、`external_links`、`modules`、`notifications`、`project_external_links`、`project_members`、`search_projection`、`task_groups`，以及 `project_archive_requests` 的 `NO ACTION`），审计链按 [ADR-008](ADR-008.md) 只追加；要么连业务历史与审计链一起删掉，要么在同一事务里按外键顺序清空 12 张子表。两者都与 AGENTS.md 第 6 节冲突。
3. 因此删除被定义为**项目退出全部可见范围**：保留行与全部历史，仅从列表、详情、搜索、动态、通知与项目级读写中排除。

## 决策

### 1. 删除是软删除，不物理删除任何历史

迁移 `0027_project_soft_delete.sql`：

1. `app.projects` 新增 `deleted_at TIMESTAMPTZ` 与 `deleted_by INTEGER`。
2. `projects_deleted_by_users_id_fk`：`deleted_by` → `app.users(id)`，`ON DELETE restrict`，与 `created_by` 一致（删除者可能随后被停用，但不得被物理删除而丢失「谁删的」）。
3. `projects_deleted_state_check`：`((deleted_at IS NULL) = (deleted_by IS NULL))`，两列必须同时为空或同时有值。
4. 迁移内 `DO` 块自校验存量数据一致，否则整体回滚。
5. 只加列与约束：不改已有列、不改数据、不递增 `row_version`、不写审计。

**不**级联删除、**不**加 `ON DELETE CASCADE`、**不**引入「隐藏项目」的额外布尔列——`deleted_at` 一个判据足以表达「已删除」，避免出现第二种真相。

### 2. 已删除项目占用项目编码

`projects_code_unique` 保持不变：已删除项目的 `code` 仍被占用，新建项目不能复用。项目编码是审计记录、迭代记录与外部链接里引用的历史标识，允许复用会让历史指向错误对象。

### 3. 删除后对所有人不可见（含管理员）

`deleted_at IS NULL` 被加进项目的每一处读取路径：

- `PostgresProjectQueryPort.list()` / `find()`（项目列表与详情）；
- `PostgresProjectAccessQueryPort` 的管理员范围、成员范围与 `checkProjectForWrite`（搜索范围、跨域写校验）；
- `PostgresProjectMembersQueryPort.listActiveMemberProfiles`（成员资料授权探针，无权时返回 `undefined`）；
- `PostgresProjectsWritePort.findProject` / `findProjectForChange`。

因此删除后：`listProjects` 不再返回、`listModules` / 任务 / 记录 / 搜索 / 动态 / 通知的有效范围都不再包含该项目；按 ID 访问统一 404（不泄露存在性）。**没有「已删除项目仍可浏览」的例外**——需要追溯历史时走审计读取（`getAuditLogs`）与数据库只读连接，而不是把它留在产品界面上。

> 2026-09-28 由 [ADR-050](ADR-050.md) 修订本节的绝对表述：被删除的项目本身仍对所有人不可见（本节其余内容不变），但「谁在何时删除了哪个项目」这条事实对全部登录用户可见——它以**项目动态流里的普通一行**呈现（`listProjectDeletions` 提供项目 ID 与名称，`getProjectActivity` 仅对该行放行 `PROJECT_DELETED`），管理员另可在审计日志里按 `PROJECT:<id>` 链读取完整审计。

### 4. 权限：只有系统管理员与本项目组长

`ProjectRoleGateService.projectDeleterRole()` 与 `roleSetterRole` 同源但单独成方法（防止未来「成员可管理」的改动把删除权顺带放大）：

| 调用者 | 结果 |
| --- | --- |
| 系统管理员（`is_admin`） | 放行 |
| 本项目 ACTIVE `LEADER` | 放行 |
| 本项目普通成员 | 403 `PROJECT_DELETE_FORBIDDEN`「只有项目组长或系统管理员可以删除项目」 |
| 非本项目成员 / 已移除成员 | 404 `PROJECT_NOT_FOUND`（不泄露存在性） |

组长判定使用**实时成员关系**（`findActiveRole`，不缓存进 Session），因此组长被转移、降级或移除后立即失去删除权。

### 5. 幂等重放的授权复核（`projectDeleteReplayAuthorizer`）

删除成功后项目对所有人不可见，`manageRole` 必然返回 `NOT_MEMBER`，直接复用会让同一个幂等键的合法重放从 204 变成 404。契约因此为这条路由声明了专用 `currentReadAuthorizer: "projectDeleteReplayAuthorizer"`，由 `projectDeleterReplayRole()` 只看**保留**的成员关系（不过滤 `deleted_at`）复核「如果项目还在，这个人现在还能不能删」：

| 重放时的状态 | 结果 |
| --- | --- |
| 系统管理员 | 204（重放原结果） |
| 仍是本项目 ACTIVE `LEADER` | 204 |
| 已降级为普通成员 | 403 `PROJECT_DELETE_FORBIDDEN` |
| 已被移除 / 已转移组长后被移除 | 404 `PROJECT_NOT_FOUND` |
| 换了另一个账号用同一个幂等键 | 404（幂等记录按操作者隔离） |

HTTP 层据此在删除操作上**跳过**可读性预检（其余操作保持原样），由上述复核替代；当前认证（Session 有效、用户未被停用）仍由 HTTP 层在调用前完成。

### 6. 契约、并发与副作用

- 路由：`DELETE /api/v1/projects/{projectId}`（`deleteProject`），响应 **204 无正文**；请求无 body，`If-Match` 必填（`ProjectVersionHeaders`），`csrfPolicy: "required"`，`idempotencyPolicy: "idempotencyRequired"`（幂等契约版本 `1.0.0`，`noBody` 重放策略），`authPolicy: "session"`，`lockOrder: ["project"]`，`retry: "none; project FOR UPDATE, expected row_version"`。
- 并发：`SELECT ... FOR UPDATE` 后重读 `row_version`，再条件更新 `WHERE id = $1 AND row_version = $2 AND deleted_at IS NULL RETURNING id`；版本不符 409 `PROJECT_VERSION_CONFLICT`，已被删除时条件更新无命中，同样以版本冲突收口（不会二次写审计）。
- 同事务副作用：审计 `project.delete`（不可变，含项目编码与名称）、项目动态 `PROJECT_DELETED`（`visibilityScope: "MEMBER"`，摘要「删除了项目 …」）。**不发通知**——删除后项目对所有人不可见，通知里的深链会成为死链；通知无法被删除或批量作废（[ADR-035](ADR-035.md) 只允许标记已读），因此刻意不发。

### 7. 前端

- `ProjectManagementModals.tsx` 的「编辑项目」弹窗**页脚最左侧**提供「删除项目」入口（`className="danger-button footer-leading"`，复用 `.calm-action-footer > .footer-leading` 的既有约定），只在 `canDeleteProject(isAdmin, currentUserRole)` 为真时渲染；右侧仍是「取消 / 保存修改」，表单区不再重复该入口，后果说明由二次确认弹窗承担（`tone="danger"`、`icon="alert"`、warning Alert 说明后果、确认按钮 `primary-button danger-button`）。
  - 2026-09-28 按用户指示「删除按钮移到弹窗页脚最左侧」调整：入口原先位于表单底部的危险说明区（`project-danger-zone`），现移到页脚靠左，与常规的取消/保存分开，避免与保存类操作混淆。
- `canDeleteProject(isSystemAdmin, role)`（`project-query.ts`）：`isSystemAdmin || role === "LEADER"`；角色来自 `ProjectDetailResponse.currentUserRole`（服务端实时计算），不在前端推断成员关系。
- 删除成功后由 `useDeleteProject` 失效项目列表、项目概览、我的任务、任务看板、动态与通知缓存；列表页就地刷新并给出提示，项目模块页离开该路由回到 `/projects`。

### 8. 与项目归档的关系（ADR-043）

ADR-043 已下线项目归档与归档申请；本 ADR **不恢复**归档，也不引入「待审删除」或「删除申请」。删除是即时、无恢复入口的单一动作；若将来需要「可恢复的删除」，必须新增 ADR 并把恢复流程与权限一并定案。

> **2026-09-28 修订（[ADR-051](ADR-051.md)）**：本节中「不可撤销、无恢复入口」已被修订——用户要求删除记录那一行同时提供还原与彻底删除，因此现在有恢复入口（系统管理员或本项目组长执行 `POST /projects/{projectId}/restore`，清空软删除标记）与不可撤销的物理删除（仅系统管理员执行 `POST /projects/{projectId}/purge`）。本节其余表述不变：仍不引入待审删除或删除申请，删除本身依旧即时生效。

### 9. 非目标

1. 不做物理删除、不做级联清理、不做「回收站」与恢复入口。（**本条已由 [ADR-051](ADR-051.md) 修订**：彻底删除与还原已定案，物理删除经 `app.purge_project` 窄口在单一事务内按外键序清理；仍不提供「回收站」列表与批量操作。）
2. 不新增项目编码回收、不复用 `code`。
3. 不给普通成员删除权，也不做「成员投票删除」。
4. 不新增 `projects.status` 取值（`DELETED` 之类的状态会与 [ADR-043](ADR-043.md) 的三态口径冲突），删除只用 `deleted_at` 表达。
5. 不为删除新增进程内锁或重试：并发删除由条件更新与行版本收口。
