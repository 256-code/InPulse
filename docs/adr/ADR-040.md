# ADR-040：任务支持平权多负责人（关联表取代单一负责人列）

- 状态：Accepted
- 基线固化：2026-09-22
- 修订关系：取代「`app.tasks.assignee_id` 单一负责人」的数据模型与契约口径（功能设计 F-14/F-16/F-32 的负责人语义、技术设计的任务读模型与写命令、权限矩阵中负责人相关条目）。任务状态流转规则（TODO/DOING/DONE/CANCELED）、迭代记录生成口径、聚合组（F-23/F-24）与遗留项转任务（F-22）的既有语义不变，只把「负责人」由单值替换为集合。

## 背景

产品要求「一个任务可以指派多个人」，交互沿用新建项目时的多人添加。此前 `app.tasks.assignee_id` 是单一可空列，配套 `tasks_assignee_status_idx` 与部分读模型假设负责人是标量，无法表达协作任务。

## 决策

1. **数据模型**：新增 `app.task_assignees(task_id, user_id, project_id, created_at)` 关联表。主键 `(task_id, user_id)` 保证同一任务不重复指派；复合外键 `task_assignees_task_project_fk (task_id, project_id) → app.tasks (id, project_id)` 把归属钉在任务所属项目上、阻止跨项目串联，`user_id` 外键指向 `app.users`；索引 `task_assignees_user_idx (user_id, task_id)` 支撑「我的任务」与负责人筛选。
2. **平权语义**：多名负责人地位相同——均可被通知、均在「我的任务」与看板中可见、任一负责人均可推进状态与编辑任务；不引入「主/次负责人」概念。
3. **回填与收缩**：迁移 `0020_task_assignees.sql` 按 `tasks.assignee_id` 逐行回填并在同事务内建立触发器与授权；迁移 `0021_contract_task_assignees.sql` 删除 `tasks.assignee_id` 与 `tasks_assignee_status_idx`。两步分离遵守 expand/contract：回填验证通过后才收缩，历史迁移不改写。
4. **数据库防线**：触发器 `task_assignees_active_assignee` 通过 `app.require_active_task_assignee()` 校验「负责人是活跃用户且是该项目活跃成员」，`FOR SHARE` 锁 `app.users` 与 `app.project_members`；`task_id`/`user_id`/`project_id`/`created_at` 由不可变列触发器保护；`app_runtime` 只有 `SELECT/INSERT/DELETE`（无 `UPDATE`），改派以「删旧行 + 插新行」表达，保留被改派前的成员历史语义。
5. **契约**：请求字段 `assigneeId` 由 `assigneeIds: number[]` 取代（`min(1).max(20)`，服务端去重并按用户 ID 升序规范化）；响应 `TaskItem.assigneeIds` 为集合，同时保留派生标量 `assigneeId = assigneeIds[0]`，让仍按标量渲染的既有读端口（看板、聚合组、我的任务列表项）无需同一批改造，**集合是唯一真相**，两者不一致时以 `assigneeIds` 为准。
6. **读模型类型安全**：Drizzle + postgres-js 对 `timestamptz` 原样传递文本，`TaskReadModel.dueAt` 必须是 `Date`。任务读端口统一采用「原始行接口（`dueAt: string | null`）+ 边界映射（`mapTaskReadRow`）」结构，禁止把字符串时间直接下发给契约校验。
7. **锁读实现约束**：`FOR UPDATE` 与 `LEFT JOIN LATERAL` 同时出现会被 PostgreSQL 拒绝（SQLSTATE `0A000`，`CheckSelectLocking`）。锁定的任务读查询必须使用标量子查询（`(SELECT array_agg(...))`）聚合负责人，不得为了可读性换回 LATERAL 连接。
8. **幂等契约版本**：`assigneeIds` 同时改变请求与响应结构，属破坏性契约变更，`createTask`/`updateTask` 由 `1.0.0` 升至 `2.0.0`、`transitionTask` 由 `2.0.0` 升至 `3.0.0`、`completeTask`（含模块变体）由 `1.2.0` 升至 `2.0.0`；`archiveTask`/`restoreTask`/模块变体继承 `updateTask` 的版本。旧 Key 在新契约下 409。
9. **校验与错误**：请求体校验失败（空数组、非正整数、超过 20 人）返回 422；负责人不是当前项目活跃成员返回 422 `TASK_ASSIGNEE_INVALID`；数据库触发器的外键违例作为最终防线，不替代应用层校验。
10. **前端**：新建/编辑任务、遗留项转任务使用多选（`CalmSelect multiple`），标签沿用「指派给」，至少选择一人；列表与详情以「、」连接展示多名负责人，未指派显示「未指派」。

- 迁移：`0020_task_assignees.sql`（建表、复合外键、触发器、索引、`app_runtime`/`app_backup` 授权、回填）、`0021_contract_task_assignees.sql`（删除 `assignee_id` 与旧索引）；迁移检查 `pnpm db:migrations:check` 通过（22 条）。
- 契约与生成物：`tasks.zod.ts`（`assigneeIds` 与派生 `assigneeId`）、`task-routes.ts`/`task-completion-routes.ts`（字段与幂等版本）、5 个生成产物（OpenAPI、指纹、客户端）；`pnpm contract:validate`（108 条路由）、`contract:drift`、`permissions:check`（108/108）通过。
- 后端：`task-management.repository.ts`（聚合读、`replaceAssignees` 幂等集合写入）、`task-query.port.ts`（原始行 + 映射）、`tasks-management.service.ts`（成员校验、仅通知新增负责人、REOPEN 接收人）、`project-member-task.command-port.ts`（改派保留其他负责人）、`my-task-query.port.ts` 与任务组、遗留项工作流的 `EXISTS` 归属判定。

- 测试：真实 PostgreSQL 集成覆盖多负责人创建/编辑/改派、去重与升序规范化、非成员 422、通知只发给新增负责人、「我的任务」按集合命中、看板与聚合组端口、`task_assignees` 索引使用；API 集成 50 文件 481 例（2 例为 ADR-039 既有 `PROJECT_ADMIN` 残留失败，与本决策无关）。
