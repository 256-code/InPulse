# ADR-051：项目还原与彻底删除

- 状态：Accepted
- 基线固化：2026-09-28
- 接受依据：用户 2026-09-28 指示——「给删除项目的动态的原始快照按钮边上加一个还原项目和彻底删除，还原项目就是把项目显示出来，彻底删除就是从硬性删除」。这条指示同时否掉了 ADR-049 第 8 节「不提供恢复入口」与 ADR-050 非目标第 1 条「不恢复被删除项目、不提供删除撤销」的取舍。
- 修订关系：**修订 [ADR-049](ADR-049.md) 第 8 节**（原先以「物理删除要么删掉审计链、要么按外键序删光全部子表」为由拒绝提供彻底删除与恢复）与 **[ADR-050](ADR-050.md) 非目标第 1 条**（原先明确不恢复、不提供撤销）。ADR-049 的软删除语义、删除权限、幂等口径，以及 ADR-050 的删除记录可见性与「动态流内普通一行」的呈现方式全部不变。
- 关联：[ADR-008](ADR-008.md)（审计只追加，本 ADR 第 3 节给出被彻底删除项目的审计链唯一例外）、[ADR-019](ADR-019.md)（写接口幂等）、[ADR-031](ADR-031.md)（管理员高风险操作只要求完整管理员 Session）、[ADR-033](ADR-033.md) / [ADR-039](ADR-039.md) / [ADR-048](ADR-048.md)（组长与项目角色）、[ADR-050](ADR-050.md)（删除记录对全部登录用户可见）。

## 背景

1. ADR-049 把删除做成**软删除**：`app.projects.deleted_at` / `deleted_by` 两列，项目退出全部可见范围但行与历史保留，且当时判定「不做回收站、不做恢复」。ADR-050 随后补了读取侧，让「谁在何时删除了哪个项目」对全部登录用户可见。
2. 用户在同一天提出反向需求：删除记录那一行旁边要能**撤销**（还原项目）也要能**抹掉**（彻底删除）。两个动作语义相反、不可逆性也完全不同，因此必须分别定权限、分别定审计与分别定数据边界，而不是合成一个「删除/恢复」开关。
3. 软删除已经解决了可逆的一半：还原只需清空两列，不需要任何数据搬回。真正没有实现过的是**物理删除**——`app_runtime` 在业务表上没有 `DELETE` 权限（迁移 `0001` 只授 `INSERT` / `SELECT` / `UPDATE`），且项目被 12 张表以 `ON DELETE restrict` 外键引用，还有「未分类模块禁删」「任务必须有状态历史」等防线与 `PROJECT:<id>` 审计链。

## 决策

### 1. 两条新命令路由，动作方向相反但都挂在删除记录这一行上

```
POST /api/v1/projects/{projectId}/restore  →  restoreProject  →  200 ProjectDetailResponse
POST /api/v1/projects/{projectId}/purge    →  purgeProject    →  200 ProjectPurgeResponse
```

- **为什么不是 DELETE/PUT**：`DELETE /api/v1/projects/{projectId}` 已经是软删除（ADR-049），HTTP 语义已被占用；彻底删除是同一资源上的第二个、语义更强的命令，用 `POST .../purge` 表达「执行一个不可撤销动作」比复用 DELETE 更不容易被误用。还原同理用 `POST .../restore`，与删除对称、可幂等重放。
- 两条路由都是写命令：`authPolicy: "session"` + `csrfPolicy: "required"` + `idempotencyRequired`（`Idempotency-Key` 必填），`versionPolicy: "none"`、`behaviorHeaders: []`（**不接受** `If-Match`：目标版本由 `deleted_at` 状态与行锁决定，客户端拿不到也不会持有被删除项目的 `rowVersion`），`auditAction` 分别为 `project.restore` 与 `project.purge`。
- 幂等契约版本均为 `1.0.0`，请求摘要覆盖 method、operationId、契约版本与 `projectId`；两条路由都登记了带版本的 `idempotencyReplayPolicy` 与 `replayAuthorizationPolicy`（详见第 5 节）。

### 2. 权限：还原沿用 ADR-049 的删除权限；彻底删除收窄到系统管理员

| 命令 | 允许 | 拒绝 |
| --- | --- | --- |
| `restoreProject` | 系统管理员；本项目 ACTIVE 组长（LEADER） | 普通成员与项目管理员（PROJECT_ADMIN）403 `PROJECT_RESTORE_FORBIDDEN`；非成员 / 已移除成员 / 项目不存在 404；项目未删除 409 `PROJECT_NOT_DELETED` |
| `purgeProject` | 只有系统管理员 | 其余一律 403 `PROJECT_PURGE_FORBIDDEN`；项目不存在或已被彻底删除 404；项目未删除 409 `PROJECT_NOT_DELETED` |

- 还原与删除**同权**：能删就能还原，不需要第二个角色参与，也不引入「待审删除」，避免出现「删得掉、还原不了」的死角。
- 彻底删除是**组织级不可逆动作**，组长（含项目管理员）不参与，与 ADR-049 第 5 节「高风险动作不下放」的边界一致。
- 授权全部在服务端按 actor、资源真实归属与**实时**成员关系判定（ADR-012 / ADR-039 / ADR-048），不读客户端提交的 `projectId` 证明归属，也不缓存角色到 Session。
- 系统管理员执行 `purgeProject` 时不再要求密码或 TOTP（ADR-031 已取消重认证），门禁是：当前有效的完整管理员 Session + `is_admin` + 写操作 CSRF + 数据库级幂等 + 审计留痕 + 前端二次确认。

### 3. 彻底删除的数据库边界：SECURITY DEFINER 窄口 + 事务级豁免

- 新增 `app.purge_project(p_project_id INTEGER)`（`SECURITY DEFINER`，迁移 `0028_project_purge.sql`），只有它是删除路径；`GRANT EXECUTE ... TO app_runtime`，`REVOKE ALL ... FROM PUBLIC`。**不**逐表给运行时角色授予 `DELETE`——那会永久放大运行时的写权限。
- 函数内部 `fail closed`：目标必须 `deleted_at IS NOT NULL`，否则 `RAISE EXCEPTION 'project % is not soft deleted'`。因此「绕过软删除直接抹库」在数据库层也不成立，删除权限口径（ADR-049）无法被这条路径绕过。
- 删除顺序固定为从叶子表到 `app.projects`（与 `scripts/purge-test-data.mjs` 的夹具清理顺序同源），覆盖 27 处：变更记录版本-遗留项关联 → 记录外部链接 → 记录影响功能 → 记录版本 → 遗留项转任务关联 → 记录的遗留项 → 迭代记录 → 任务影响功能 → 任务组成员关系 → 任务状态历史 → 任务负责人 → 任务外部链接 → 任务 → 任务组 → 功能外部链接 → 功能 → 项目外部链接 → 模块 → 遗留归档申请 → 编码序列 → 项目成员 → 通知 → 活动投影 → 搜索投影 → 外部链接 → `audit_logs` → `audit_chain_heads` → `projects`。删除 `projects` 断言恰好 1 行，否则整体失败。
- `modules_protect_unclassified` 由「永远拒绝删除未分类模块」改为「**仅**当同一事务内 `app.purge_project_id = 本行 project_id` 时放行」：豁免只能由 `app.purge_project` 通过事务级 `set_config(..., true)` 打开并在返回前复位，其他任何路径（含未来新增的代码路径）仍然 fail closed。延迟约束触发器（`projects_bootstrap_complete` / `project_members_bootstrap_complete` / `project_members_leader_complete`）在提交时因项目行已不存在而直接返回，无需额外处理。
- 项目**自己的** `PROJECT:<id>` 审计链随项目一起删除（这正是「彻底删除」的语义），**SYSTEM 链不受影响**——这是 ADR-008「审计只追加」的唯一例外，且例外范围被函数写死、无法针对其他链触发。
- 事务内无网络请求、无长任务；全部删除在一个事务里完成，失败即整体回滚。

### 4. 还原：清空软删除标记，不搬数据

- `restoreProject` 只做 `SET deleted_at = NULL, deleted_by = NULL, updated_at = now(), row_version = row_version + 1`，条件带上 `deleted_at IS NOT NULL`；命中 0 行即 409 `PROJECT_NOT_DELETED`（并发还原只有一个能成功，另一个按状态冲突拒绝）。
- 因为软删除从未搬走任何数据，编码、成员关系、模块、功能、任务、记录、审计链与通知在删除期间保持原样，还原后**立即恢复删除前的全部可见性与权限**，不需要任何补偿写入，也不重发通知。
- 还原写项目动态 `PROJECT_RESTORED`（`visibilityScope: "MEMBER"`）与审计 `project.restore`（写入**项目自己的** `PROJECT:<id>` 链，此时该链仍存在），响应返回还原后的 `ProjectDetailResponse`（含 `rowVersion`、`memberCount` 与统计）。
- 项目编码不因删除或还原变化；`app.code_sequences` 只在彻底删除时随项目删除。**不做编码回收**：彻底删除后重新创建项目拿到什么编码由当时的序列状态决定，不保证沿用旧编码，也不保证不复用。

### 5. 幂等与重放的授权复核

- 两条路由都用既有幂等机制（`Idempotency-Key` + 摘要 + 数据库记录），重放前**重新验证当前认证、当前角色、目标状态与结果资源的当前可读权限**，任一门禁失败即拒绝且不泄露已存状态码或响应体。例如组长在首次还原后被降级或移除，用同一把 Key 重放不会拿到成功结果。
- **还原**的重放复核沿用常规项目可读性判定（`projectCurrentReadAuthorizer`）：还原成功后项目本身重新可见，因此按当前成员关系与项目角色重新判定即可，与首次执行的门禁（组长 / 管理员）同源。
- **彻底删除**的重放语义尤其关键：项目行与它自己的审计链都已不存在，任何项目内资源复核都不再成立，因此走专用门禁 `projectPurgeReplayAuthorizer`——只复核「当前 Session 仍是有效的系统管理员」。同一个系统管理员用同一把 Key 重放拿到同一份统计（`ProjectPurgeResponse`）；换成他人、换 Key 或已不是管理员一律拒绝（403/404）。
- 两个 2xx 响应都已登记 `safeBodyFieldPaths`（还原为项目详情字段，彻底删除为七项计数），响应 Schema 与重放策略同契约版本绑定，请求或安全重放策略变化必须升级契约版本（旧 Key 在新契约下 409）。

### 6. 前端：入口就在删除记录那一行

- 删除记录行（项目动态流里 `PROJECT_DELETED` 的普通一行，ADR-050）的「原始快照」按钮旁并列两个动作：**还原项目**（次要按钮）与**彻底删除**（危险按钮）。
- 入口由服务端下发的 `canRestore` / `canPurge` 决定：此前端只隐藏按钮，**不作为授权依据**——两个字段只是渲染提示，真正判定在服务端（ADR-039 的口径）。
- 彻底删除必须二次确认（弹窗明确写「不可撤销、项目全部数据与该项目审计链将被删除」）；还原不需要二次确认（可逆）。
- 两个动作完成后刷新删除台账与项目动态；失败按统一错误体展示（403 / 404 / 409 分别给文案）。

### 7. 非目标

1. **不**提供回收站列表、批量还原或批量彻底删除；台账一行两个按钮即全部入口。
2. **不**提供「彻底删除后再恢复」——物理删除不可撤销，这是本 ADR 与软删除的核心区别。
3. **不**恢复项目编码，**不**保留被彻底删除项目的审计正文（只保留 SYSTEM 链上那条 `project.purge` 记录）。
4. **不**把彻底删除下放给组长或项目管理员，也不为它引入待审流程。
5. **不**修改被删除项目的可见性口径：彻底删除后它本来就不可见，只在删除台账里消失；`PROJECT_DELETED` 动态行随该项目的活动投影一起被删除。
6. **不**为还原或彻底删除发站内通知（还原后可继续工作，通知只会产生悬挂深链；彻底删除后项目不存在，更无收件人范围）。

## 后果

- 删除记录行成为「可撤销的删除」与「不可撤销的抹除」两个动作的共同入口，用户在界面上就能完成两条路径，不需要管理员手工执行 SQL。
- 物理删除的权限面被压缩到「系统管理员 + 一次显式确认 + 一条窄口函数」，运行时的表级 DELETE 权限、软删除的 fail closed 校验与未分类模块的防线都保持原样。
- 不可逆动作的代价被明确写出：项目业务历史、`PROJECT:<id>` 审计链与删除记录本身都会消失，只剩 SYSTEM 链上的一条 `project.purge`。
