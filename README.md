# InPulse

软件研发功能迭代记录与任务协作系统，用于统一管理项目、模块、功能、任务、迭代记录及其历史关系。

> 当前状态：设计阶段。系统设计 V1.0.2 尚待开发基线冻结，技术设计 V1.2.2 为候选实施版，须通过阶段 0 门禁。当前仓库尚未包含可运行应用、构建脚本或开发与测试命令。

## 项目目标

InPulse 面向国内单企业、单实例的软件研发团队，目标规模为 10～300 名用户，重点保证：

- 任务、迭代记录、合并关系和操作历史可追溯；
- 核心业务操作保持事务一致，不丢失数据、不串项目、不产生半完成状态；
- 权限、并发冲突和数据库不变量可由自动化检查验证；
- 1～3 人、以 AI 编码代理为主要生产力的团队可以长期维护。

## 计划范围

本期计划交付：

- 用户登录、系统管理员和项目成员两类角色；
- 项目、成员、模块与功能档案管理；
- 功能级和模块级任务，以及指派、完成、取消、恢复和历史查询；
- 三段式迭代记录、草稿、发布与版本管理；
- 遗留问题转任务，以及任务合并、来源分支和解除合并；
- GitHub Issue、Pull Request、Commit 多链接关联；
- 全局搜索、项目动态、站内通知和操作审计。

以上均为候选设计范围，不代表当前仓库已经实现。

## 候选架构

```text
浏览器
  -> Nginx
       -> / 与 /assets/*：React SPA 静态资源
       -> /api/v1/*：NestJS 模块化单体 API
                         -> PostgreSQL
```

| 层次 | 候选基线 |
|---|---|
| 语言与工程 | TypeScript 严格模式、pnpm monorepo |
| 前端 | React、Vite、Ant Design、TanStack Query、React Hook Form、Zod |
| 后端 | NestJS、REST JSON `/api/v1`、Zod Schema + Route Registry |
| 数据 | PostgreSQL、Drizzle ORM、显式数据库迁移 |
| 测试 | Vitest、真实 PostgreSQL 集成测试、Playwright |
| 部署 | 多阶段镜像、Docker Compose、Nginx |

具体主版本、锁定策略和架构约束见[技术设计](./技术设计v1.2.2.md)。NestJS 11.x/12.x 迁移决策、生成工具组合、nonce CSP 兼容性、搜索可行性及实际补丁/digest 仍须在阶段 0 验证。

本期明确不计划引入微服务、多租户、Kubernetes、Redis、Elasticsearch、WebSocket、Event Sourcing、CQRS 框架、通用 Outbox 或 GitHub API/Webhook 深度集成。

## 基线冻结前阻断项

候选设计仍有少量冲突和缺失资料。开始受影响功能前必须先完成定案；唯一维护清单和代理处理要求见[仓库开发规则](./AGENTS.md#13-已知基线阻断项)。

## 实施阶段

1. 阶段 0：跑通 monorepo、契约、数据库、认证安全、搜索 PoC、容器和最小 CI；
2. 阶段 1：用户、管理员、项目、成员、模块、功能、权限与审计基础；
3. 阶段 2：任务、迭代记录、遗留项、幂等、并发和同事务投影；
4. 阶段 3：任务合并、历史关系和依赖边界检查；
5. 阶段 4：搜索、通知、生产部署、备份恢复和完整 E2E 验收。

各阶段完整验收条件见[技术设计第 14 章](./技术设计v1.2.2.md#14-实施顺序)。
